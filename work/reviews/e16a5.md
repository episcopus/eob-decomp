## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E16A5.C:4: the unit header says DispatchKeyWait "tag[s] it". Only DispatchKey ORs the 0x8000 tag in (`key |= 0x8000`); DispatchKeyWait passes the WaitKeyEvent value to DispatchNodeEvent untagged (evidence: the two function bodies; the 0x41/0x42 mouse branch in DispatchNodeEvent is reached only by the untagged path, since its `key < 0` test is always true for DispatchKey).
- [ ] must-fix src/E16A5.C:55: the callback30 comment says "0 stops the walk", which is backwards. DispatchNodeEvent runs `if (changed && head->callback30) more = !head->callback30(head);`, so a nonzero return stops the walk and 0 lets it go on.
- [ ] must-fix src/E16A5.C:112 and :169: `g5E20` is described as "nonzero when the mouse moved since the last call" and the dispatcher as redrawing "unless ... the mouse has not moved (ds:5E20)". Every write in src/ is list construction, not mouse motion: EOV0.C:368 (BuildRowNodeList sets `g5E20 = 1` after it links the row list; the comment at EOV0.C:352 says so) and EOV1.ASM:2454 (the text-window clip, see EOV1.ASM:2180). No mouse code in src/ writes it. Say what the code shows (a flag that forces the walk to redraw after a list is built or changed) or leave it `Purpose unknown:` with those callers as the evidence.
- [ ] must-fix src/E16A5.C:140: "only an event with bit 0x100 is accepted" is wrong. An event without bit 0x100 is passed to DispatchNodeEvent unchanged. Bit 0x100 only gates the three code ranges that clear it (`if (key & 0x100) ... key &= ~0x100`). Nothing is rejected.
- [ ] must-fix src/E16A5.C:164: "it returns the event it consumed, or 0" is wrong. The end of DispatchNodeEvent is `if (result == 0) result = key; return result;`, so a keyboard key that no node takes comes back as itself; only a mouse-only call (key set to 0) returns 0. Both callers ignore the value, which the comment could say.
- [ ] must-fix src/E16A5.C:176: "that ORs the node's flags +0E mask into ds:5DEA" does not describe the four cases. They set `changed`, the state's 4 bit, the on bit and `result`; none writes a g5DEA word. ds:5DEA is written only in the redraw loop (`g5DEA[0] |= head->flags & 0xaa04`, :255) and read in the release test (`mask = g5DEA[g5E1C]`, `mask = g5DF2[g5E1E]`). Words 1..4 are read as masks.
- [ ] must-fix src/E16A5.C:513: the DrawNode caller list names 1658:01E6 "ResetNode". src/E1658.C:231 names that address `ClearNode` (the packet says the same); no ResetNode exists in E1658.C.
- [ ] should src/E16A5.C:37: "the inactive bit and the layout bits E1658.C names". E1658.C:42-50 describes the +0E bits as the button-mode selectors (0x0100, 0x0400, 0x1000, 0x4000) and the inactive mark (0x0008); it never calls any of them layout bits. Name what each bit selects, or say which are not named.
- [ ] should src/E16A5.C:15-23 (struct Region): `saved0..saved3` names the bytes at +8..+E. src/E082C.C:24-35 names the same offsets attr1, attr2, column, row (attr1 and attr2 marked [H]), and E1A29.C:20 calls them "four words of saved state". Pick one name set for both files and record it (`make rename` covers the names, the struct field names are per file).
- [ ] should src/E16A5.C:87: gDrawText takes `void far *text` here. src/E082C.C:65, src/E14EF.C:81 and the other declarations take `char far *text`. Use the same parameter type; the bytes are the same.
- [ ] should src/E16A5.C:74 and the uses at :283, :285, :316 (`state |= 2`), :446 (`state &= ~6`), :472, :544: the value 0x0008 is named NODE_STATE_8, which is the value and not the meaning (READABILITY, Constants). src/E1658.C:86 names the bit 0x0002 NODE_STATE_2 and src/E1658.C:89 names 0x0008 NODE_STATE_PREV ("the previous on" reading), and E1658.C:80 says E16A5.C calls it NODE_STATE_8. Use the E1658.C names (NODE_STATE_PREV, NODE_STATE_2) so the two files agree, and write the literal 2 and 6 as the named bits.
- [ ] should src/E16A5.C:519-544 (DrawNode locals): `st1`, `st4`, `st8`, `st10` name the bits, not what they mean. `st1` is the on bit (NODE_STATE_ON), `st8` the previous-on bit (see the item above). Names like `isOn` and `wasOn` say it; `st4` and `st10` can take the names of their #defines.
- [ ] should src/E16A5.C:681: "main calls it once as (0, 0L) ... (E07C8.C:151)" is a stale line cite into another file. The call is now at src/E07C8.C:264. Cite the caller by address instead: "called from 07C8:0001 Main" (the packet's called-by list).
- [ ] should src/E16A5.C:509: "5 or 0 draws a box through DrawBox or gDraw8066" is loose. Kind 5 always draws a box. Kind 0 draws only in the cases the code shows: modeB or modeC is 2 (DrawBox), or modeB is 3 with bit 0x0008 set, or modeC is 3 with bit 0x0010 set (gDraw8066), and only when both bits 0x0001 and 0x0004 are clear.
- [ ] should src/E16A5.C:180: "The pointer is hidden and shown around the redraw" is in the DispatchNodeEvent paragraph, but that function never calls HidePointerZone or ShowPointerZone; DrawNode does (its own comment says so). Move the sentence to DrawNode's comment.
- [ ] should src/E16A5.C:176: "the jump table at 16A5:07BB (16A5:07B3)" has no evidence in src/ or docs/design. Cite where the table was read (a disassembly listing or the map) or mark the address [H].
- [ ] should src/E16A5.C:138 (DispatchKeyWait comment): "Called once per frame by overlay 0 (ovl0:00F7) ..." The packet lists the callers, but nothing in src/ shows a per-frame loop around them. Cite the loop (for example ovl0:00F7 WaitKeyOrPause in EOV0.C) or drop "once per frame".
- [ ] should src/E16A5.C:7: the claim that 0xC6/0xC7 are the mouse buttons has evidence (src/EOV0.C:1176, "the mouse's confirm keys 0xc6/0xc7"; and the test at src/EOV0.C:1210) but no citation here. src/E14EF.C:229-230 covers only 0x41/0x42. Add the citation.
- [ ] should src/E16A5.C:166: "(1 or 3 when bit 0x800 is set, else 2 or 4 by GetKeyState)" reads as if the 2/4 values depend on bit 0x800. In fact GetKeyState sets 2 or 4 on every call, and a button event then overrides it with 1 or 3 (by bit 0x800). Say that.
- [ ] should src/E16A5.C:316-520 (DispatchNodeEvent body): many flag bits are unnamed (0x20, 0x40, 0x80, 0x100 to 0x8000 apart from the inactive bit), along with the mask 0xaa04 (:255) and the masks 0xf00/0xf000 (flagsLow and flagsHigh). READABILITY rule 4 wants a name where the meaning is known. Name the bits E1658.C already names; leave the rest as values with a `[H]` comment. flagsLow and flagsHigh could say left and right button bits (their use is by g5E1C and g5E1E).
- [ ] note src/E16A5.C:74 and the "pressed" reading of bit 0x0004 (the struct comment at +2E and the DispatchNodeEvent paragraph): src/E1658.C:86-90 does not call it pressed. The dispatcher sets it when `pressedFlag` is set (cases 1 and 2 with modeC). Tag the reading [H] or say "the mark the dispatcher sets for a press".
- [ ] note `gFC82` (the extern, line ~100): this file gives "which key word matched, 1 or 2". src/E0ACD.C:22 and :168-187 read the same global as an action mode with branches 0, 1 and 2. The values agree; the cross-file reading should be mentioned in one of the two comments, since the names are shared.
- [ ] note `build/packets/e16a5.md` lists ds:805E as `tile` and ds:8066 as `x1` (both "E16A5.C"). This file uses gDraw805E and gDraw8066, as src/E1658.C:14 and src/E1DE7.C:67 do. The packet's global list is stale, not this file.
- [ ] note `SetNodeCallback(int arg, long value)`: `arg` is ignored by design (its word push is the reason, src/E07C8.C:170-173). The comment carries that; the name is a placeholder and can stay.
- [ ] note DrawNode's local `type` is the node's `kind` field; `kind` would match the struct. `more` in DispatchNodeEvent means "the walk goes on"; `walkOn` says it. Neither is wrong.
- [ ] note `f1A29_000F` is a placeholder extern with no comment in this file; src/E082C.C and the packet name it the same. It is fine as a placeholder.
- [ ] note the unit header's compile claim (the -B flags line keeps the restart tails separate, the e14ef idiom) is supported by the matcher result, not by a citation. Acceptable as it stands.

## Summary

The unit is understandable from its source alone: the five functions are named for what they do, the callers and callees carry addresses, and most constants are named. Seven must-fix items remain. Two comments say the reverse of the code (the callback's 0/nonzero rule, and the key filter in DispatchKeyWait). The g5E20 flag is described as a mouse flag, though the only writers in src/ build lists. The return value of DispatchNodeEvent, the write to ds:5DEA, the DispatchKeyWait tag claim and the ResetNode name are each wrong as written. The names that stay placeholders are the flag bits, the colour pairs and the mode bytes; the comments already mark those [H]. The two struct Region field names and the NODE_STATE names disagree with src/E082C.C and src/E1658.C and should be aligned. Nothing escalated: no matcher, spec or pin question.
