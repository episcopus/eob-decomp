- [ ] should src/I0921.ASM:1: "256 colours of three 6-bit components" describes the DAC, which is 6 bits wide (tools/oracle/ega.py:232 masks the written value with 0x3F). The routine copies the buffer's bytes unchanged, so the buffer's values are 6-bit only if the palette data is. Nothing in src/ or WHITEPAPER 4.2 shows that (WHITEPAPER 4.2 calls these bytes palette bytes [H]; src/I0AED.C:131 and :185 say the same, and E1B82.C:131 and :185 are its twin). Say "the DAC takes the low six bits of each byte" for the hardware fact, and mark the buffer's width [H] or leave it open.
- [ ] should src/I0921.ASM:9: "Every register it uses is saved" is true (AX, CX, DX, SI, DS, BP are all pushed and popped), but the flags are not: `xor ax,ax` and `inc dl` change them and the routine does not save them. A port has to know that, so say "the flags are not preserved".
- [ ] should src/I0921.ASM:26: the label `next` names the loop's byte read, which is not what the word means in this file. `nextByte` or a label named for the copy (the loop writes one colour component per pass) says what the code does.

The packet finds no direct call, and no other `src/` file names this segment or the routine (`re/symbols.toml` has evidence `segment` only). That is enough for a name taken from the behaviour (the header says what it does), but the next reader should know no caller is known, so a caller found later would be worth recording here.
- [ ] note src/I0921.ASM:1-2: the leading underscore is the C linkage name, which the other ASM units use too (src/E17A6.ASM:102, `_DirectionFromPoints PROC FAR`). Nothing to change.
