## Findings

- [ ] must-fix src/E0CF7.C:5 (`struct Node { int a; int b; }`, and the uses at lines 10, 12, 21 to 23): the type claims a record of two ints; the bytes say a link. `ListAdd` (1658:001E..0072) walks `p = *(void far **)p` until `p->[0] | p->[2] == 0` (1658:0032..004C), then stores the new item as a far pointer at offset 0 of the last node (0054, 0057) and zeroes the item's first 4 bytes (005E, 0063), returning the saved head (0069..006C). So offset 0 is one far pointer `next`, and `ListInit` (0CF7:0007) zeroes exactly that (two word stores, `a = 0; b = 0`, are the two halves of a null far pointer). `a` and `b` are the halves of `next`, not two ints. Use `struct Node { struct Node far *next; }` (the matcher will say whether it still matches; the stores to offsets 0 and 2 should be the same) or at least rename the fields to `next_off`, `next_seg`. The nodes are also not 4 bytes: every table entry points into DGROUP at a 60-byte (0x3C) stride (ds:3A9E, 3ADA, 3B16, ... in segment 212E, all with a relocation), each record starting with its link.

## Summary

The unit matches and is small and readable, but its one type is wrong in a way that matters for every later unit that touches these lists: `struct Node { int a; int b; }` is really a far `next` pointer at offset 0 of a 60-byte DGROUP record (proved by `ListAdd` at 1658:001E and by the table contents), and the header comment describes the data the wrong way round. Both are must-fix; they do not change the bytes. The names `gFlag`, `gList`, `gTable*`, `BuildList*` are acceptable placeholders (no evidence yet for the real meaning, and the review file records the evidence collected so far: the 0/1 writers of ds:F3B9, the 60-byte stride, the consumer `16A5:005A`).
