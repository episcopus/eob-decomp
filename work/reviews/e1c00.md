## Summary

Round 4 (main 694b89b): review fails on two must-fix items, both about the caller. The unit is nearly
understandable from its source alone: the request layout, the 0FA00h MemAlloc with flag 20h, the 4B03h
parameter block, the two entry calls, the MemRealloc call and the mouse flag's polarity all check against
the bytes. What is still wrong is the name of the caller: 07C8:0199 is StartupGame, not main, and its
failure path returns to Main, which shuts the program down. Shoulds: the overlay list (five names, not
four), the two-call description, the [H] on the entry's return values, the mouse value that Main sets
after start-up, and the failure path's pop order. Placeholders that stay for lack of evidence: the
overlay-loader words DGROUP:818Ah to 8194h (with the relocation word at 818Ch that no file in src/ writes),
the entry arguments 27h and 1A16h (what the entry does with them is not established), the pad byte at
1C00:0001 (a lone 0 byte [H]), and the name g8148.

Round 3 (main 7c3b967): review fails on three must-fix items. The round 2 fixes hold, and the bytes support what the comments say about the mechanics: the caller's request build and failure print (07C8:0245 to 0258, 0265 to 0283, read on the disassembly), the MemAlloc flag 20h return (`MK_FP(seg + 1, 0)`, E19BC.C), the 4B03h parameter block at ES:BX = DGROUP:818Ah ([H] DOS EXEC function 03 layout), the entry call at segment:0 through 818Eh, the MemRealloc arguments and the failure path's pop order. What a reader cannot take from this file is the mechanism and the mouse flag. The header calls the unit VROOMM, but VROOMM is the INT 3Fh runtime trap, and this unit loads named driver overlays on request.
