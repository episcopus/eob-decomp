## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E1C00.ASM:24: "Allocate an 0FA00h byte block of DGROUP" is wrong. The block is a far heap block from MemAlloc (19BC:0007, src/E19BC.C:34-75, MemAlloc returns `MK_FP(seg + 1, 0)` for flag 0x20). Only its segment word goes into DGROUP:818Ah. Say "allocate a 0FA00h byte far block (MemAlloc, flag 20h)".
- [ ] must-fix src/E1C00.ASM:26-27: "load the overlay named by DS:DX into the load block ES:BX = DGROUP:818Ah" misreads INT 21h/4B03. ES:BX is a parameter block: word 0 is the segment to load at (the word stored at DGROUP:818Ah, line 56), word 1 is the relocation factor (DGROUP:818Ch). The oracle reads it the same way and adds the factor to each relocation (tools/oracle/dos.py:634-649). Describe the block at ES:BX as the parameter block.
- [ ] must-fix src/E1C00.ASM:75: "call the loaded overlay's entry at segment:0000 with (0, 1A16h, 27h)" lists the wrong arguments. The code pushes the overlay segment (`mov ax,ds:[818Ah]`, line 102, `push ax`, line 106), then 1A16h (lines 107-108), then 27h (lines 109-110). The 0 is only the call target offset, stored at 818Eh (line 104), not an argument. Say: pushes the overlay segment, 1A16h, 27h, so the entry's first argument is 27h and its third is the overlay segment.
- [ ] should src/E1C00.ASM:24-25: "keep its segment" is true, but the reason is not in the comment. `or ax,dx` (line 50) leaves the segment in AX because MemAlloc returns offset 0 for flag 0x20 (19BC:0007). Without that sentence a reader takes `mov es:[bx],ax` (line 56) for an offset store.
- [ ] should src/E1C00.ASM:25-26: "save SP and SS across the call (INT 21h/4B03 uses the caller's stack)" gives a reason with no evidence. Nothing in the bytes, the oracle or the whitepaper shows that 4B03 uses the caller's stack. Say the reason is not established [H], or drop it.
- [ ] should src/E1C00.ASM:27-28, 30: the header says "It is called near" and declares `PROC NEAR`, but the function ends with `retf` (line 69) and its caller does `push cs; call` (line 99). It is a near call with a pushed CS, so it returns far. Say so, or the PROC NEAR and retf look like a mismatch to the next reader.
- [ ] should src/E1C00.ASM:72-77 (1C00:0055 comment): the side effects are missing. The function writes ds:818Ah to 8190h, 818Eh, and on success ds:814Ah when ds:8148h is nonzero (lines 142-144). ds:814Ah is `g814A` (src/E07A9.C:26, tested at E07A9.C:82, `if (!g814A)`), and ds:8148h is the driver present flag that src/E1BF3.ASM:4 and :45 describe. The comment should name both, with their evidence, as the globals this function changes.
- [ ] should src/E1C00.ASM:75-76: "scale its return by 16 and MemRealloc a record of that size" is vague. The entry returns AX (stored as the function offset at 818Eh, line 104) and BX in paragraphs (four `shl bx,1`, lines 113-116, which make bytes). MemRealloc (19BC:018A) resizes the overlay's own block at seg:0 to that size and keeps its contents, so it is not a new record. Say that, and what AX and BX are.
- [ ] note src/E1C00.ASM:73-74: the request's word at +2 (DS:8123, written by the caller at 07C8:0251) is never read by 1C00:0055. Say so, so the next reader does not assume the request has three fields that matter.
- [ ] note src/E1C00.ASM:73 and the packet: the caller's lcall is at 07C8:0259 (the pushes of DS and the offset 8121 start at 07C8:0254). The packet's "called by 07C8:0199" is the enclosing function's start (see e1a65.md, e1a47.md). Both are consistent; the comment is fine as it stands.
- [ ] note src/E1C00.ASM:56 and the DGROUP parameter block: the relocation factor at DGROUP:818Ch is never written by any file in src/ (grep finds 818A, 818E, 8190, 8192, 8194 only). Whatever it holds at run time is the DGROUP initial value unless something else writes it. Check it in the oracle before relying on it in a port.
- [ ] note src/E1C00.ASM:49-58 and 124-146 (failure paths): a load failure (INT 21h CF, line 139 region) or a failed MemRealloc or entry call leaves the 0xFA00 block allocated; nothing frees it. The caller prints "Could not load overlay" (07C8:0260 `cmp ax,0FFFFh`). Candidate QUIRK mark (`QUIRK 1C00:0002`/`1C00:0055`: no free on failure) once it is checked whether the program exits after the message.
- [ ] note src/E1C00.ASM:123-137: the entry's return is checked only on the second call (`jb short failsub`, line 139). The first call's AX and BX are used without a check. Keep as is; the header says nothing about it.
- [ ] note src/E1C00.ASM (names): DGROUP words 818Ah, 818Eh, 8190h, 8192h, 8194h, 8148h are unnamed in this file; they are overlay-loader state (block segment, entry offset and segment, saved SP and SS). If the whitepaper gets names for them, use them here and in the header. ds:814Ah is already `g814A` (E07A9.C).
- [ ] note the two names are evidenced: `_LoadOverlayImage` (MemAlloc of 0FA00h with flag 20h, INT 21h/4B03 load, BX 0/FFFFh, src/E1C00.ASM:30-63) and `_RunOverlayRequest` (the caller 07C8:0259 builds the request at DS:8121 from the ds:3074/3076 tables, calls the entry and compares AX with -1 at 07C8:0260). No must-fix on the names.

## Summary

The unit is small and its two names are backed by evidence: `_LoadOverlayImage` (a 0FA00h far block
from MemAlloc, a load with INT 21h/4B03) and `_RunOverlayRequest` (its caller at 07C8:0259 compares AX
with -1 and prints "Could not load overlay"). The source is understandable without the bytes except in
three places: the block is described as "of DGROUP" (it is a far heap block), the 4B03 parameter block
is described as a "load block", and the arguments the overlay entry receives are listed in the wrong
order with a 0 that is not pushed. Each is a must-fix, with the code lines as evidence. The side effects
of 1C00:0055 (g814A, ds:8148h) are missing from its comment. The overlay state words at DGROUP:818Ah to
8194h have no names; they are placeholders, which is fine until the whitepaper names them. Review
failed until the three must-fix items and the side effects are corrected.
