## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E1B82.C:18: "(19BC:0059)" is the wrong address. 19BC:0059 is `je 0x31`, the end of
  the retry test in the loop (19BC:0057 to 0059). The code for `MK_FP(FP_SEG(blk) + 1, 0)`
  (E19BC.C:59) is at 19BC:00B3 (`inc ax`) and 19BC:00B4 (`mov [bp-4], 0`). Cite 19BC:00B3.
- [ ] must-fix src/E1B82.C:81-83: "the case bodies are laid out in source order 0, 3, 1, 2, 4, the
  order of the table at cs:020d" is wrong. The table at cs:020D is indexed by format value and lists
  the cases 0, 1, 2, 3, 4 (00E7, 011E, 0176, 010D, 01CC). The bodies are in the code in the order
  1B82:00E7 (0), 010D (3), 011E (1), 0176 (2), 01CC (4). Say that: the bodies follow the source order
  0, 3, 1, 2, 4 (1B82:00E7, 010D, 011E, 0176, 01CC), and the table is indexed by value.
- [ ] should src/E1B82.C:81-82: "the original keeps the cbw;cwd; C++ codegen does that here, the C front
  end folds (int)(long)*src to *src" is hard to parse. Suggest: "The original sign-extends the format
  byte (cbw; cwd) and switches on the int in AX. The C++ front end (-P) emits those bytes; the C front
  end folds the extension away (re/symbols.toml note on 1B82:00C7)."
- [ ] should src/E1B82.C:113-119: the case 4 comments say "(src+2)", "(src+6)" and "src+8+n" for block
  offsets, but the local `src` is advanced at line 114 (`src += 2`), so each comment means a different
  pointer from the one the line uses. Say "block offset +2" and so on, or keep the block base in its own
  pointer.
- [ ] should src/E1B82.C:75-76: "Unpack1/Unpack2 use a 0x3C00/0xFC00 byte work buffer". The bytes show
  the sizes Unpack allocates (1B82:011E..0131 for 3C00h, 0176..0189 for FC00h). How much of the buffer
  the decoders use is not shown here: E1D9A.ASM has a 3C00h limit for format 1 (lines 317, 350) and no
  FC00h compare anywhere in the unit. Say "gets" or "allocates" here. (WHITEPAPER 147 says the same;
  that is for the whitepaper's owner.)
- [ ] should src/E1B82.C:58 and :66-67 (LoadPacked): `n` holds the packed block's byte length (the
  comment on line 66 says so). `n` is for counters (READABILITY, Names). Name it `packedLen`.
- [ ] note src/E1B82.C:88 (Unpack's `n`): it is the palette byte count at src+6. The first round kept
  `n`. Keep it: the claim "palette bytes" comes from WHITEPAPER 147 and tools/re/wwfmt.py; the pinned
  data shows only that the field is 0 (checked above), so the comment on line 117 should keep saying
  where the palette claim comes from.
- [ ] note src/E1B82.C:43 and :48 (LoadFile): "mode 1" is a bare number. 1C0E:00DB dispatches modes
  1, 2 and 3 to three different branches (1C0E:00E6..00F3), and no file in src/ names the mode. Leave
  it as "mode 1"; when 1C0E is in src/, name the constant.
- [ ] note src/E1B82.C:5-9 (header): "only the C++ front end keeps the format byte's sign extension to
  long" rests on the tc100/tc101 trials recorded in the re/symbols.toml note on 1B82:00C7. Say "in the
  tc100/tc101 trials", since no other compiler was tried.
- [ ] note src/E1B82.C:120: `long size` passed to `int len` truncates at the call. The comment on line
  120 says the decoder uses only the low word (1D9A:003B), which is right. Keep it.
- [ ] note src/E1B82.C:129-132 (SetUnpackBuffer): `if (gBufSeg = seg) ;` is the shape the bytes need
  (a store, then `or ax, ax`). Keep it; the comment at 125-126 explains it.
- [ ] note: the format-numbered names Unpack1..Unpack4 and the placeholder f19EC_0002 stay as they are.
  E1D9A.ASM:8 says the names come from E1B82.C, and E19EC.C still names f19EC_0002 as a placeholder.

## Summary

The unit reads well from its source: the names of the four functions, the globals gBufSeg and gBufSize,
the callees (FileOpen, MemAlloc, f19EC_0002, Unpack0 to Unpack4) and the parameter names all agree with
the bytes and with the other files of `src/`. Two comments say something the bytes do not show: the
address of the flag 0x20 allocation (19BC:0059 should be 19BC:00B3) and the order of the switch table
(it is indexed by format, not in source order). Those are the must-fix items. Also: `n` in LoadPacked is
a length, not a counter, and the case 4 comments mix block offsets with the advanced local `src`. The
format-numbered names Unpack1..Unpack4 are placeholders by design (the 1D9A unit takes them from
their callers).
