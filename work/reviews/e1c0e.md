## Findings

### Round 1 (this round): nine must-fix, eighteen shoulds, notes

- [x] must-fix src/E1C0E.C:3: "a slot in a ten entry table of cached files (the records at ds:01FF, ...)" is wrong about the count. The records at ds:01FF are 203 entries (the table ends at the first empty name, record 203, EOB.EXE file offset 23CDF plus 19 per record). Ten is the number of DOS handle slots (MAX_FILES, gFileHandles at ds:FEEA). Say that. Evidence: the parse of the image above; `MAX_FILES` at src/E1C0E.C:83. FIXED: the header now says the table at ds:01FF runs to the first empty name (203 records in this image) and that ten is the DOS handle slots (MAX_FILES, gFileHandles at ds:FEEA).
- [x] must-fix src/E1C0E.C:139 to 142 (RetryFile): the comment says it upper-cases "from the last backslash of `name` on". The bytes do not do that. The loop (1C0E:0060 to 0086, back edge `jne 0x60` at 0086) sets `base` to the backslash that `strchr` found, and the next `strchr` finds that same backslash, so a name that contains a backslash never leaves the loop. A name without one is upper-cased whole (1C0E:0088). Mark this `QUIRK 1C0E:0060:` with what happens, and fix the comment to say what the code does. Also wrong in the same comment: "FileOpen modes 0 and 2" (these are RetryFile modes; FileOpen has no mode 0), and "1C0E:0EE7/0F6E mode 0xB" (BuildFileCache, 1C0E:0F6E, calls no RetryFile; only 1C0E:0EE7 does). Evidence: `tools/re/disasm.py eob/EOB.EXE 1C0E --start 0x46 --len 100`; no name in the 203-record table holds a backslash. FIXED: the RetryFile comment now marks QUIRK 1C0E:0060 (a name with a backslash never leaves the loop, a name without one is upper-cased whole), gives the codes as RetryFile modes with their gErrorText texts, and drops the wrong FileOpen/0F6E claims (only 1C0E:0EE7 calls RetryFile with 0xB).
- [x] must-fix src/E1C0E.C:165 to 168 (FileOpen): "mode 2 (write) and mode 3 (read/write) delete and recreate the file, retrying on failure" is wrong for mode 3. Only mode 2 calls DeleteFile; both modes run `ResetFile` (which deletes and recreates) only when `CheckFile` fails, and then with retries. Say that. Also "reports code 1" is RetryFile mode 1, whose message is index 1 ("Illegal MODE in Open_File.") before the fatal code 0xC. Evidence: the fall-through from `case 2` (src/E1C0E.C:192 to 197) into `case 3` and the message table above. FIXED: the FileOpen comment now says mode 2 deletes and recreates, mode 3 does not delete, both run ResetFile through RetryFile mode 0 while CheckFile fails, and the bad mode reports RetryFile mode 1 ("Illegal MODE in Open_File.") before the fatal 0xC.
- [x] must-fix src/E1C0E.C:190, 193 and 203 (FileOpen): `access = FILE_IN_MEMORY | O_RDONLY` (and WRONLY, RDWR) puts the value 0x8000 into the open flags that `open()` receives. In this file's own fcntl constants (src/E1C0E.C:93 to 97) 0x8000 is O_BINARY, not the in-memory bit, and the same value is the bit that FILE_IN_MEMORY is named for. Write `O_BINARY | O_RDONLY` (and so on): the bytes are the same. Evidence: the `open(name, access, ...)` call in the not-in-memory branch; `O_BINARY 0x8000` in the header. FIXED: the three access stores now read `O_BINARY | O_RDONLY`, `O_BINARY | O_WRONLY`, `O_BINARY | O_RDWR` (same bytes), and the comment says O_BINARY.
- [x] must-fix src/E1C0E.C:429 (CheckFile): "a missing file (open failed) reports 0xF" is wrong. A file that LocateOverlayFile cannot find makes CheckFile return 0 with no code; the caller then retries or gives up. Only a file that was located and then fails to open reports 0xF (the FatalError(0xf) after `open`). Code 0xF is "Internal Error in File_Exists()" in the message table, not a missing-file message. Say that. FIXED: the CheckFile comment now says a file LocateOverlayFile cannot find returns 0 with no code (the caller retries or gives up) and only a located file that fails to open reports 0xF.
- [x] must-fix src/E1C0E.C:675 to 678 (BuildFileCache): "Nothing happens when no entry is flagged" is false. The first loop still frees every slot (`gFileHandles[i] = SLOT_FREE`), upper-cases every name and clears every data pointer before the `count == 0` return. Also, the address `1C0E:1042` is inside `les bx, [bp-6]` (1C0E:1041, 3 bytes). The index store is `mov es:[bx], ax` at 1C0E:1049 after `add bx, ax` at 1C0E:1044. Cite 1C0E:1044 and 1C0E:1049. Evidence: `tools/re/disasm.py eob/EOB.EXE 1C0E --start 0x1030 --len 30`. FIXED: the BuildFileCache comment now says the two clear loops run before the count==0 return, and cites 1C0E:1041 (les bx), 1C0E:1044 (add bx, ax) and 1C0E:1049 (store) instead of the 1042 that is inside the les.
- [x] must-fix src/E1C0E.C:807 to 808 (ExpandTextWindow): "width and height grow by twice `cells`" is wrong in the unit the declaration gives for gTextHeight (ds:FE60, pixel rows). The code adds `cells * 16` to the height and moves the top by `cells * 8` pixel rows. So "twice cells" is right only in 8-pixel lines, and the comment does not say so. Give the units: top moves up 8 pixel rows and height grows by 16 pixel rows per cell, width by 2 columns. FIXED: the ExpandTextWindow comment now gives the units: left/width in 8-pixel columns (width grows 2*cells), top moves up cells*8 pixel rows and height (ds:FE60) grows cells*16 pixel rows per cell.
- [x] must-fix src/E1C0E.C:851 (LoadFileSlot): "the file is opened (through the aliased entry when the slot's link is negative ...)" is wrong. The own-file branch tests `entry->link > 0`, so every link <= 0 takes the alias branch, and link 0 takes it too (the alias is gFiles[0 & LINK_INDEX], the entry itself). The image has link 0 on INTRO.EXE (record 0), so an INTRO.EXE load would look for its own directory. Nothing loads it now (its flags are 0), but the comment must say so, and the branch is a QUIRK: mark `QUIRK 1C0E:144E:`. FileOpen and CheckFile test `link < 0` for aliases, so the two tests disagree. Say that too. FIXED: the LoadFileSlot comment now says the own-file test is `entry->link > 0` (1C0E:1520, jle at 1C0E:1525) so link <= 0 takes the alias branch (link 0 aliases the record itself, INTRO.EXE record 0), marked QUIRK 1C0E:144E, and notes the disagreement with FileOpen/CheckFile.
- [x] must-fix src/E1C0E.C:851 to 856 (LoadFileSlot): "A failed allocation, open or read frees the copy and returns 0" is wrong for the second allocation. After EvictFile returns 1, `data = MemAlloc(entry->size, 0)` is not tested, so a NULL copy goes on to `open` and `read(fd, data, size)`. Mark `QUIRK 1C0E:144E:` (the untested second allocation) and say what happens. Also "the tail `mov ax,1` after the failure block (1C0E:1603)": 1C0E:1603 is `cdq`. The success path's `jmp 0x163d` at 1C0E:1629 lands on 1C0E:163D, which is where the tail is. Cite 1C0E:163D. Evidence: `tools/re/disasm.py eob/EOB.EXE 1C0E --start 0x1603 --len 58`. FIXED: the LoadFileSlot comment now marks QUIRK 1C0E:144E (the second MemAlloc at 1C0E:1508 after EvictFile is untested) and cites the tail 1C0E:163D, reached by the jmp at 1C0E:1629, not the cdq at 1C0E:1603.

## Summary

Round 1 finds the unit understandable, but not yet right. The names of the functions and of the main globals hold against the bytes, the image, the message table and the other units: the file cache is a table of 203 entries with 10 DOS slots, aliases point at the PAK records, and the error dialog's messages match the codes. The nine must-fix items are where the text says something the code does not do: the RetryFile loop (it never leaves a name that has a backslash), the FileOpen mode-3 claim and the O_BINARY name, the CheckFile missing-file claim, the BuildFileCache "nothing happens" claim and its address, the ExpandTextWindow height units, and the LoadFileSlot alias test, the untested second allocation and the 1603 citation. The shoulds are mostly names of locals and placeholders, the mixed "slot" and "record" vocabulary, and undocumented quirks that a port must keep. No escalation: the matcher and the spec are not in question, and each finding has a source-level fix.
