## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] should src/E1A63.C:1: the header says the handler "records the error code and returns to the program". The store is real (`mov ax,[bp+6]; mov [FE5E],ax` at 1A63:0007..000D), but `gHardErr` is written only here: a search of EOB.EXE, the overlays in build/re/eob-overlays, INTRO.EXE and START1.EXE finds no other absolute reference to ds:FE5E (no `a1`, `8b 06`, `3b 06`, `83 3e` read of it). So nobody reads it, and "error code" is the meaning Borland gives the handler's first argument [H], not something the game's own code shows. Say "write-only in the binaries searched" in the comment, or keep the name as a placeholder (the header does say "Placeholder names", but `gHardErr` reads as confident).
- [ ] should src/E1A63.C:1: "returns to the program" is incomplete: the call is `hardretn(0)` (push 0 at 1A63:0010..0012, then far call to 0000:608A), so the program gets error value 0 back. Worth saying "returns to the program with error 0". The callee is runtime library (`_hardretn` = 24714 = 0x608A in build/re/rtl_compare.json), so the semantics come from the library name, not from our reading of its body.
- [ ] should src/E1A63.C:7: the type of `harderr` is declared `void (*handler)(int)`. Borland's handler takes four ints and returns int. This matches the bytes (one argument at [bp+6], nothing returned; hardretn does not come back), so it is fine; say in a comment that the declaration is narrowed on purpose, so nobody "corrects" it to the library prototype and loses the match.
- [ ] note The "int 24h" claim in the header is supported: the first bytes of `_harderr` at 0000:604C store the handler far pointer to ds:FFD6/FFD8, then push 0x0024 and a stub offset (cs:6014) and call a far routine at 0000:6003 (set vector pattern; `_setvect` is the likely callee, not checked by name). So InstallHardErr hooks DOS interrupt 24h.
- [ ] note The `-G` claim is supported by the bytes: `44 44` (`inc sp; inc sp`) after the 1A63:0014 call in HardErrHandler and `83 c4 04` (`add sp,4`) after the call in InstallHardErr; whitepaper section 2 line 39 lists e1a63 with the other `-G` units.
- [ ] note Sizes and structure check out: 42 bytes at 1A63:0004, a 21 byte handler then a 21 byte installer; InstallHardErr pushes 1A63 and 0004 (a far pointer to HardErrHandler), and it has one caller, 07C8:0001 (the packet shows e07c8). HardErrHandler has no direct caller, as expected for an address that DOS invokes. `make match FILE=src/E1A63.C` reports 2 of 2 match.

## Summary

The unit is small and understandable from its source alone. The function names follow the Borland runtime names it calls (`harderr`, `hardretn`), which are proven on our bytes through rtl_compare.json, and the int 24h purpose is confirmed from the bytes of `_harderr`. The one weak spot is `gHardErr`: it is written once and read nowhere in any of the shipped programs, so its meaning ("hard error code") is borrowed from the Borland convention and should be flagged as such. The three `should` items are comment clarity only; no must-fix.
