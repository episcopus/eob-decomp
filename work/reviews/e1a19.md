## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E1A19.ASM:30 (comment of `_IsLastLogicalDrive`): "AL = 1 means the call is unsupported (DOS before 3.0)" states a DOS version with no evidence on our bytes. The code only shows that AL = 1 on error is treated like "yes" (1A19:0050..0052) and that AL = 0Fh is not. From recall [H] (not checked on a source here) IOCTL 44h/0Eh arrived in DOS 3.2, so "before 3.0" is probably wrong as well. Drop the version, or write "AL = 1 (invalid function, [H] DOS without 44h/0Eh)" and tag the version as [H]. The same file calls AL = 0Fh "invalid drive"; that is the DOS error code table, also recall [H], and fine to keep tagged.
- [ ] should src/E1A19.ASM:40 and :17: the call sites are given as "1C0E:1369" and "1C0E:13E7". Those are not call addresses: the packet's "called by" column lists the start of the calling function (1C0E:1310 and 1C0E:13E7). The actual calls are `lcall 1A19:003B` at 1C0E:136A (the `push si` argument is at 1369) and `lcall 1A19:0006` at 1C0E:13F2. Say "called from the function at 1C0E:1310 (call at 136A)" and "from the function at 1C0E:13E7 (call at 13F2)".
- [ ] should src/E1A19.ASM:15 (`_FindLastDrive`): "stops failing with AL = 0Fh" is ambiguous. The walk (1A19:0028..002F) stops when CF is clear OR when the error is anything but 0Fh (`jae found`, `jne found`); only AL = 0Fh with CF set moves to the next lower drive. Also the function returns nothing: AX is pushed at 1A19:0009 and popped at 0038, so the `mov ax,dx` at 0031 is not a return value (the caller at 1C0E:13F2 ignores AX anyway; it only reads gLastDrive). Say "returns nothing (AX preserved)". There is no lower bound: if every call failed with 0Fh, DX would pass 0 and go negative; harmless in practice, note only.
- [ ] note Names: `gLastDrive` (ds:FF00) is evidenced: 1C0E:1361 reads it (`mov al,[ff00]`) as the first drive of the loop that calls `_IsLastLogicalDrive` down to 0 (`dec si` / `cmp si,-1`, 1C0E:13A3..13A7). `gDefaultDrive` (ds:FF34) is written only (1A19:0010); a scan of the image for `a0/a2/80/8a ... 34 ff` found no reader in EOB.EXE, so the name rests on the INT 21h/19h call alone. It is correct but nothing uses it; do not read more into it.
- [ ] note `_IsLastLogicalDrive` returns 1 when the device has a single logical drive (AL = 0 after CF clear, 1A19:0056), when AL-1 == DL (this letter is the last one mapped to the device), and also on error AL = 1; any other error or a different last letter gives 0. The comment says this correctly except that "physical device" should read "block device" if the [H] reference wording is wanted. The name is a fair placeholder; what the caller does with the result is not yet known (the loop at 1C0E:1369 only runs when byte ds:81EA is non-zero, 1C0E:1358).
- [ ] note The two `push bx` / `pop bx` pairs in `_IsLastLogicalDrive` (1A19:003E and 0043) save BX twice; harmless, a hand-written idiom, the match proves it is as in the original.
- [ ] note The 6 bytes at 1A19:0000..0005 belong to the previous unit (they disassemble as the tail `add sp,4 / pop bp / retf`); the unit correctly starts at 0006. The same code is in INTRO.EXE (unit i0992, same_as e1a19); DGROUP offsets differ there, as the header says.
