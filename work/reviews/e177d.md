## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E177D.C:57-61, :70-86 (PlaySound): the comment says "the sign of the number gates the speaker (gSpeakerOn)". The sign never gates anything. `gSoundMap` is declared `unsigned char` (src/E177D.C:13, src/E07A9.C:30), so `driverSound` is always 0..255 and the tests `driverSound < 0` (:76) can never hold. The matched code keeps the test, but it cannot fire. What really happens: a nonzero number sets gSpeakerOn to 1 (:80 to :82, the Tandy driver, per src/E1948.ASM:7 "1 is Tandy, 0 is PC speaker") and nothing ever sets it to 0. Say so, and mark the dead test `QUIRK <address>:` (the address of the `< 0` compare in 177D:0070). The same holds for the `gCurSound < 0` test at src/E177D.C:135 in PlaySoundVolume.
- [ ] must-fix re/globals.toml:116-117 and :119 (not a source file, but the text the source is built from): gSpeakerOn and gSpeakerMode are described as "toggled by the sign of the sound number". Same reason as above; the registry text must change with the comment. Use `make rename WHY=...` or edit the registry in the fix commit.
- [ ] must-fix src/E177D.C:99-106 (PlaySoundVolume): the comment says the function "loads the new sound's register values through 0000:03CA". The code reads gCurSound (lines 122 to 124, 145, 130), and gCurSound still holds the sound recorded by the *previous* call; the new sound number is stored only at the end (line 150). So a call restarts the previously recorded sound (`f0_400C(gCurSound)` at :130, or `StartSound` of `f0_03E3(gCurSound)` at :145 to :146) and records the new one. The new sound is started only by a later call, and the first call after load (gCurSound 0, line 114) starts nothing. Evidence: the bytes behave this way for the matched code, lines 114 to 150. Confirm in the oracle before the fix marks it `QUIRK 177D:0106:` (it looks like an original bug, not a decompile error). Fix the wording: "retunes and restarts the sound recorded by the previous call (gCurSound), then records the new sound and volume".
- [ ] must-fix src/E177D.C:99-106 (PlaySoundVolume): the conditions in the comment are wrong. The comment says the restore happens "when a sound is already playing" and that for "a volume above zero" it "starts it (0000:400C on AdLib...) and pokes the driver register gDrvReg". The bytes: on AdLib (gSoundCard 0) the restore, the reload, the start (`f0_400C`, line 130) and `gDrvReg = 0x0B` (line 131) all sit inside `if (gCurVolume < 0x10)` (line 116). Only the fade and the amplitude write (lines 125 to 129) depend on `gCurVolume > 0`. On the other cards (lines 133 to 147) the sound starts on every call with no volume test, and there is no restore. Rewrite the sentences to name these two conditions.

- [ ] should src/E177D.C:40-42 (LoadSoundDriver): "Called by StartupAlloc (07A9:000A)" gives the caller's entry, not the call site. src/E07A9.C:2-7 and :95 put the call at 07A9:00D2. re/renames.toml:262 says "called by StartupAlloc 07A9:0063", which contradicts it. Give the call site here (after checking the bytes), and tell the E07A9 and registry owners about the conflict (see the note below).
- [ ] should src/E177D.C:52 and :8 (header): "the far pointer 0000:03AA points at it". 0000:03AA is the address of `f0_03AA` itself (src/E177D.C:30), not a data pointer; the far pointer it returns is the block's address. Say what `f0_03AA` returns and where the block sits, or drop the segment claim. "Loaded into the code segment" is also unclear: segment 0 is named in whitepaper 2.1.2; say which segment.
- [ ] should src/E177D.C:8 and :25 (gDrvReg, 0000:3B36): "the loaded driver's register" says little. The code waits `while (gDrvReg)` (:117 to :118) before it touches the sound registers, and stores 0x0B after starting a sound (:131). So it is a handshake byte the driver clears (or sets), not a register. Say what is known: "the driver's busy flag: the program waits for it to clear before it writes the sound registers, and sets it to 0Bh after a start". If that is not known, use `Purpose unknown:`. The busy-wait loop has no comment (:117); the comment on the function should cover it.
- [ ] should src/E177D.C:57-61 and :99-106 (speaker wording): "PC speaker" is used for every card other than AdLib. `gSoundCard` 1 is the PC speaker and 2 is the Tandy speaker (whitepaper 2.4 menu: "AdLib or Sound Blaster, PC speaker, Tandy speaker"; src/E07C8.C:296 to :309). `gSpeakerMode` is 1 only on the Tandy path (src/E07C8.C:306 to :307). Name the cards: "the non-AdLib cards (PC speaker, Tandy speaker)", and say that the gate matters on Tandy only.

## Summary

The unit reads well as a loader and a player: the file name choice, the 120-byte map and the 32C8h block are described in line with the whitepaper, and the matcher-proved bytes agree with the names of the four functions. Its two playing functions do not describe their behaviour correctly, though. The sign of the sound number never gates the speaker (the map is unsigned), and PlaySoundVolume restarts the sound recorded by the previous call instead of the one it was given, with the AdLib work under a volume test the comment leaves out. The must-fix findings are comment and registry text only (one in re/globals.toml, three in src/E177D.C); the bytes do not change. Placeholder names remain for the 0000-segment helpers and the 17A6 function, which belong to other units. `gDrvReg`, `gSoundLevel`, `gSoundAmp` and the magic numbers in PlaySoundVolume need their evidence or a `Purpose unknown:` note.
