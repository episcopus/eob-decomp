## Round 1

### Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/S_TEXT.ASM:8 (header): "The probes at 056A, 05BA and 05E6 (reached only through the table, and past the unit's end) are not written here." The unit's declared 827 bytes run from 0239 to 0573, so 056A is inside them, and the claim that the probes are past the end is wrong for 056A. The three probes are contiguous: the VGA probe at 056A is 80 bytes (its ret is at 05B9), the EGA probe at 05BA ends at 05E5, the CRTC probe at 05E6 ends at 05F5, and PutChar (s_lib, 05F6) starts right after. The 0574 end comes from the whitepaper (2.4, "OVRHP at 0574h") and from the map's InitVideo entry, but the bytes at 0574 are probe code. Evidence: `make match FILE=src/S_TEXT.C` prints "unit s_text not complete: ours 605 bytes, the unit 827" (and the ASM has 212), so 056A to 0573 (10 bytes) are declared but written nowhere. Needs the human's decision on the unit boundary (escalated); this item cannot be fixed by a comment alone.
- [ ] must-fix src/S_TEXT.C:49-50 (Main header): says the three execl arguments are one-character arguments `"0" + the choice`. Only the graphics argument (:105, `gSelection + '0'`) and the mouse argument (:127, `gMouse + '0'`) are "0" plus the choice. The sound argument (:113, `gArgSound[0] = gSound`) is the key character '1' to '4' itself (:108 to :110). Evidence: the bytes are in S_TEXT.C; the whitepaper 2.4 (line 117) repeats the same error, see the note below.
- [ ] must-fix src/S_TEXT.ASM:62-63 (DetectVideoAdapter comment): says it stores "0080h, 0180h or 0283h". The bytes at 0000:04E1 to 04F8 (`b4 01 b0 80 80 e2 70 74 0b b0 81 80 fa 10 74 04 b0 82 b4 03`) give AX = 0180h when the status bits 70h are zero, 0181h when they are 10h, and 0382h otherwise (AH is the high byte, so `mov ah,1` / `mov al,80h` is 0180h). The 0101h of the steady-status path is right. Fix the three values and say what selects them (the status bits 70h).
- [ ] must-fix src/S_TEXT.ASM:103-106 (NormalizeVideoInfo comment): "either word's low byte is 4 or more" is wrong for low bytes 80h and up. The compares are signed (`cmp byte ptr [di],4` then `jge`, bytes `80 3d 04 7d 25`; 7Dh is JGE, not JAE), so a low byte from 80h to FFh is negative and does not exit. DetectVideoAdapter stores low bytes 80h, 81h and 82h, which therefore do reach the mode test. Say the test is signed (4 to 127), and say what happens to the 80h and up values.
- [ ] must-fix src/S_TEXT.C:26 (`gSelection`: "the key the menu loop last read"): the variable holds the key read (:83), then the zero-based menu index (:85, `gSelection -= '1'`), then the character 'N' as the restart flag (:97). The comment is true only at :83. Say the three uses, or, if the match allows, split the variable where the uses differ (the decompiler decides).
- [ ] must-fix src/S_TEXT.C:9-12 (library routines `PutChar`, `GetKey`, `DetectMouse`, `execl`; header line 4 "the library routines are named by their address"): none of the four names has evidence in this unit, and re/symbols.toml has no name for the s_lib entries at 05F6, 0608, 0642 and 0837. The header says they are named by address, but the code names them by function. For execl the whitepaper disagrees with itself: line 117 has `spawnl(.., "INTRO.EXE", ...)` at 0000:0447, line 133 has "`execl` of INTRO.EXE". Give each name its evidence in its extern comment: the caller behaviour (PutChar prints a character at :145; GetKey reads a key at :83, :94, :109, :119; DetectMouse gates the mouse prompt at :115), or the library module it matches (rtl_compare). For 0000:0837 the name must be settled (execl or spawnl) from its bytes or its module; until then it is a claim without evidence.
- [ ] should src/S_TEXT.C:33-45 (placeholder globals gBanner to gHomie): their declarations have no comment. Their names are backed by the strings: ds:0113 is the banner ("Eye of the Beholder Version 1.9"), ds:016E is "*" (gStar, the mark of a detected mode in gNote), ds:0170 is " " (gSpace), ds:030E is "homie" (gHomie), which INTRO's main checks with strcmp (whitepaper 2.4, line 124). Put the string in each declaration, and say gHomie is the fifth execl argument checked by INTRO.
- [ ] should src/S_TEXT.C:31 (`gDetectedMode`): declared as `char`, but it is the first byte of the four-byte info record: InitVideo zeroes both words (ASM:145-146) and NormalizeVideoInfo reads the second word (ASM:109). The name and the type claim one byte. Name the record (for example in the comment: the record is four bytes, gDetectedMode is its first byte) and declare its type to match when the layout is known.
- [ ] should src/S_TEXT.C:29 (`gMode`: "the graphics mode the menu works on"): it is an index from 0 to 6 into gModeMaskTable (:67 to :71), set from gDetectedMode, or to 6 when the byte at F000:C000 is 21h. Say it is the table index.
- [ ] should src/S_TEXT.C:69 (`0xF000C000` and `0x21`): magic constants with no comment. Mark them `Purpose unknown:` and say what is known: the byte at F000:C000 is not identified in the whitepaper; when it is 21h the menu uses table entry 6 (ds:00AF = 03h, mask 03h, CGA and Tandy). Evidence: S_TEXT.C:69 to :71.
- [ ] should src/S_TEXT.C:138-139 (PrintString comment): "No frame variable survives the loop, only the index i" describes the compiler's stack frame, not the function. Say what the loop does and drop the frame sentence, or say why the local `i` must be kept (the match needs it).
- [ ] should src/S_TEXT.ASM:21-23 (StoreVideoWord): "the first word when it is zero". The code tests the low byte of the first word (`cmp byte ptr [bx],0`, :27), not the word. The values stored have a nonzero low byte, so the difference does not show, but the comment should say "the low byte of the first word".
- [ ] should src/S_TEXT.ASM:35-38 (TestCrtcRegister): "probe one CRTC register" but the register is always 0Fh (`mov al,0fh` / `out dx,al`, :41 to :42); say so. "the value in AL/AH" is unclear: AH keeps the first read-back, AL the value to write back.
- [ ] should src/S_TEXT.ASM:61-64 (DetectVideoAdapter): "a steady value means MDA" and "the adapter is CGA or EGA" are inferences from the port numbers and the status bits; the bytes show only which branch runs. Mark the identification as an inference (`[H]`) until it is checked against the oracle or the hardware.
- [ ] should src/S_TEXT.ASM:103-106 (NormalizeVideoInfo, the swap rule): the mode is the low three bits of the INT 10h AH=0Fh result (`and al,7`, :117), and "the record's byte +1 must not be 1, else it must be 1, and the two words are swapped" is ambiguous. Write it as: swap when the mode is 7 and byte +1 is not 1, or when the mode is not 7 and byte +1 is 1 (:118 to :128).

## Summary

The matched code reads well and the names that are backed by evidence are fine: StoreVideoWord, TestCrtcRegister, NormalizeVideoInfo and InitVideo each describe what their bytes do, and the menu strings back the global names. The unit is not yet understandable from its source alone, for three reasons. First, four comments say something the bytes do not: the sound argument is not "0" plus the choice, the DetectVideoAdapter values are wrong, the low-byte test in NormalizeVideoInfo is signed, and gSelection is described as one thing when it holds three. Second, the library routine names (PutChar, GetKey, DetectMouse, execl) are asserted without evidence, and the whitepaper calls the same call spawnl. Third, and most important, the unit boundary is not right: the video probe at 056A is inside the unit's declared bytes, runs past the 0574 end, and is not written in any file, so `make match` reports the unit incomplete (10 bytes). Escalated to the human (STATE=escalate) because the boundary is a map and spec question. Placeholder names left as they are: the globals gBanner to gHomie and the record name gDetectedMode, until the findings above are answered.
