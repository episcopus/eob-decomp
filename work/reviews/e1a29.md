## Findings

- [ ] must-fix src/E1A29.C:13-16 (and the globals at :23-29, the locals in :73-80): the field names `w`, `h`, `dx`, `dy` and the globals `gImgW`, `gImgH`, `gImgX`, `gImgY`, `gImgRow` say "width / height", but the evidence says the first two words are the top-left corner, not a size. (1) The initial table in EOB.EXE (DGROUP 212E, file offset 0x2800 + 0x212E0 + 0x9F, 16 bytes per record) starts `0,0,40,200` for record 0, then `8,72,24,56`, `19,64,20,128`, `29,120,8,64`: record 0 is the whole 320x200 screen (40 columns of 8 pixels, 200 lines), so word 0 is a left column in 8-pixel units, word 1 a top line, word 2 a width in columns and word 3 a height in lines. Record 3 (`29,120,8,64`) read as left, top, width, height ends at column 37 and line 184, inside the screen. (2) The wrappers add `gImgW*8` (as `gImgRow`) to x and `gImgH` to y (1A29:0032..003A), and 082C:0650..0664 does the inverse (`x - [bx+9F]*8`, `y - [bx+A1]`) before calling 1A29:000F: this is a screen-to-region-relative conversion, so the record is the origin of a screen region. (3) `gImgX = w + dx` and `gImgY = h + dy` (1A29:01AE..01CB) are then the right and bottom edges, and `gSetImage(w, x, h, y)` is called as (left, right, top, bottom). The header comment already says "origin offsets", which contradicts the field names. Rename (for example `left`, `top`, `width`, `height` in the struct; `gRegionLeft`, `gRegionTop`, `gRegionRight`, `gRegionBottom`, `gRegionLeftPx`) or keep placeholders such as `f0..f3`. A "region" or "viewport" is better than `Image`: nothing here draws an image of that size.
- [ ] should src/E1A29.C:13-20: `pad0..pad3` and "only the first four words are used here" are right for this unit but the record words 4..7 are in use elsewhere: the routine at 1DE7:0009 copies `[811D]`, `[811B]`, `[FE52]`, `[FE54]` into words 4..7 of the old record (`[bx+A7]`, `[A9]`, `[AB]`, `[AD]`) and loads them from the new one (1DE7:0022..00B0). The initial data shows small values in word 4 (15, 14, 6) and word 5 (12, 13, 2), which look like colours [H], so they are per-region saved state of globals ds:811D, ds:811B, ds:FE52, ds:FE54, not padding. Name them `saved0..saved3` or say so in the comment.
- [ ] should src/E1A29.C:1-7: "the same table 082C reads" is true (082C:0650, 0696, 06DC, 071E) but also read by 0D1C:A0F7, 0EF3:8387, 1547:1E47, 16A5:0867 and 1DE7:005F, and written by 1DE7:02FE (the setter of words 0..3, which calls 1A29:0189 again when the record being rewritten is the current one, cmp with `[8108]`). Better: "the region table at ds:009F, set by 1DE7:02FE".

I found no writer of ds:80C2, 80A6, 80D6, 80DA, 809A, 8096 or 80B6 in the resident code (searched the load module for those words), only indirect `lcall [..]` users, so they are filled at run time (the `.OVL` load, whitepaper 2.5, is the likely source). Tag it [H] or say "filled outside the resident code". The names `gDraw80C2` etc. are fine placeholders; the first parameter `a` is undetermined (a single word pushed last, the page or colour mode perhaps) and the `z` of 0107 and 0148 likewise.

## Summary

The unit is small and the logic (null check, lazy select of a record, offset the coordinates, call the driver pointer) is readable from the source. One must-fix: the struct and global names `w/h/dx/dy`, `gImgW/H/X/Y/Row` and `Image` assert a meaning (image width and height) that the initial table in EOB.EXE (record 0 is `0,0,40,200`, the full screen) and 082C's coordinate subtraction contradict: the first pair is the region's top-left, the second its size, and the globals are origin and right/bottom edges. The header comment says "origin offsets", so the file is inconsistent with itself. The `should` items concern the padding words (used by 1DE7:0009 as per-region saved text state), the incomplete list of table users, and the [H] on the driver pointer table. Function names stay placeholders (`f1A29_xxxx`) and that is fine.
