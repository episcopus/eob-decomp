## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E1A29.C:2-3 (header): "The screen is cut into the 16-byte records of the region table" is wrong: the records are not a partition of the screen, they overlap. Record 0 is the whole screen (`0,0,40,200`, which is 40 columns of 8 pixels by 200 lines), and records 1 to 3 (`8,72,24,56`, `19,64,20,128`, `29,120,8,64`) lie inside it. Evidence: the initial table in EOB.EXE at file offset 0x23B7F (DGROUP 212E, +9F, 16 bytes a record). Say that the table holds one rectangle per region and that the rectangles may overlap.
- [ ] must-fix src/E1A29.C:121 (comment on SelectRegion): "Called by every front end above and by 1DE7:02FE after it rewrites a record" is wrong for 1DE7:02FE. The call is conditional: 1DE7:0333 `cmp si, [8108]` and 1DE7:0337 `jne` skip the call (1DE7:033A `lcall 1A29:0189`) unless the record it rewrote is the current one. Evidence: `tools/re/disasm.py eob/EOB.EXE 1DE7 --start 2FE`. Fix: "and by 1DE7:02FE when the record it rewrote is the current one".
- [ ] should src/E1A29.C:35-43 (the `mode` parameter of the driver pointers and of the front ends): the name `mode` claims a meaning the evidence does not show. The one caller of `[ds:80C2]` found, 1BBE:01E0..01F4, pushes two words, the pointer shape record and two coordinates, and then the literal `0` (`mov ax, 0; push ax` at 1BBE:01F0), then `lcall [80C2]`. So the first argument, `mode`, is 0 there. A literal 0 shows a value, not what it selects. Either rename it to a neutral placeholder (for example `arg0`, used everywhere `mode` is) or keep `mode` and say in the comment that the only caller passes 0.
- [ ] should src/E1A29.C:48-51 (the comment on f1A29_000F, the `src` argument and the "Purpose unknown" text): the one caller of `[ds:80C2]` found (1BBE:01F4) passes the pointer shape record as `src` (`[816E]:[8170]`, gPointerShapeOff and gPointerShapeSeg, re/renames.toml:226 and 235), with the mouse pointer's coordinates. That is evidence for what `src` is, and it is cited nowhere in this file. Add it to the comment on f1A29_000F (keeping "Purpose unknown" for the front end's role, which is still unknown).
- [ ] should src/E1A29.C:20-32 (struct and globals): the units are not stated where they matter. `gRegionRight` (line 30) is in 8-pixel columns and `gRegionBottom` (line 32) is in lines, like `gRegionTop` and `top`. Also `region` (the parameter of the front ends and of SelectRegion) is a record index, not an offset: `gRegions[region]` is `region * 16` (1DE7:0305..0309 shifts the index by 4 the same way). Say both in the comments.
- [ ] note src/E1A29.C:26-27 (gCurRegion, "index of the region selected last"): this is the index SelectRegion sets. 1DE7 keeps its own record index at ds:811F (1DE7:0055 `mov [811F], si`, and 1DE7:0009 saves the four words into the record indexed by [811F]), so there are two indices, and this unit does not say whether they agree. The next reader should not assume they are the same variable.
- [ ] note `make packet UNIT=e1a29` lists ds:80C2, 80A6, 80D6, 80DA, 809A and 8096 as `mode`, and ds:80B6 as `left`, under "Globals src/ already names". Those are the first parameter names of the function-pointer declarations, not the global names. The packet tool should use the declared variable name. Not a source finding; for whoever owns tools/re.
- [ ] note The earlier review (rev-sonnet, git history d343823) gives the initial words 4 and 5 of the record as 15,14,6 and 12,13,2. The bytes are: word 4 is 15,14,6,15 and word 5 is 12,12,12,13 (records 0 to 3). The source comment says only "small values", so src/ is not wrong, but that review's numbers are not.

Verified (no finding): the struct layout and the initial table (record 0 = 0,0,40,200 with saved words 15,12); the field order of the setter 1DE7:02FE (words 0..3 from the arguments at bp+8..bp+0E); the save and load of words 4..7 by 1DE7:0009 (saves into [811F], loads from the new record, globals 811D/811B/FE52/FE54); the y offset in the front ends (y + gRegionTop at 1A29:002E; the x offset was matched but not read by hand); the `inc sp; inc sp` clean-up at 1A29:0029..002A that the header cites for -G; the four `gRegions` readers in the header (1DE7:005F reads [bx+9F], as listed).

## Summary

The unit is understandable from its source alone. The region record and the globals are backed by the initial table and by 1DE7's accesses, and the names from the earlier review (region, not image) hold. Two comments are wrong: the header's "cut into" claim (the records overlap, record 0 is the full screen) and the condition under which 1DE7:02FE calls the selector. Three should items remain: `mode` is a weakly backed name (the only caller passes 0), the evidence for `src` (the mouse pointer record, via 1BBE:01F4) is not cited, and the units and the index nature of `region` are not stated. Function names stay placeholders (`f1A29_xxxx`), which is fine: `Purpose unknown` is still true for the front ends' roles, and `extra` in 1A29:0107 and 1A29:0148 has no caller to show what it is. `make match FILE=src/E1A29.C` is 7 of 7 and `make readability UNIT=e1a29` is 0 findings, so the matcher and the gate have nothing to add here.
