## Findings

- [ ] must-fix src/E1BB1.ASM:1-15 and the EXTRN comments (lines 22-35): the header says the function "sets up the level view/store buffer", takes "the level's name record" and a "view origin". The evidence says it sets the mouse pointer's shape. 1BBE:0002 and 1BBE:00ED (the two routines it calls) read the same globals as a pointer sprite: 1BBE:001E..002F compute `ds:815C - ds:8158` and `ds:815E - ds:815A` where 815C/815E is the last drawn pointer position (1BBE:0111..0124 copies the pointer position 8138/813A into 815C/815E, and E1BF3 owns 8138/813A as the cursor position), so 8158/815A is a hot-spot offset subtracted from the pointer position, not a view origin; the caller passes (8,8) for n > 0 and (0,0) for n == 0 (E07A9.C:92-94, a hot spot at the sprite's centre versus its corner). 1BBE:00ED then draws the record at ds:816E/8170 through `[ds:80C2]` (pushed at 1BBE:01E0..01F4 with the clipped position 817E/8180), and moves the saved background through the buffer ds:816A/816C with `[804E]` (1BBE:00B9..00D9, in 0002) and `[80AE]` (1BBE:01B9..01D9, in 00ED). So: 816E/8170 is the pointer shape record, 816A/816C the save-under buffer for the screen behind the pointer, 8158/815A the hot spot. Nothing in the unit or its callers says "level" or "name"; `gNamesDDE4` is just the name E07A9.C gives the table the caller indexes. Rewrite the header and the EXTRN comments, or at least mark the level/name reading [H] and give this one.
- [ ] must-fix src/E1BB1.ASM:5-8 and EXTRN g8154/g8156/g80C6: width and height are swapped. 8154 is filled from record byte +3 and 8156 from byte +2 plus 1, and 1BBE uses them as: 8154 is added to the pointer's y (1BBE:0095 `add ax,[8154]`, clipped to 0C8h = 200) so it is the sprite height in pixels; 8156 is added to x>>3 (1BBE:005F `add ax,[8156]`, clipped to 28h = 40) so it is the width in 8-pixel units (the same unit as the region records of E1A29, left/width in 8-pixel units). So byte +3 is the height and byte +2 + 1 is the width, not the other way round. The call at 1BB1:0066..006F pushes 8154 (height) first and 8156 (width) second, so `[ds:80C6]` is called as (width, height) in cdecl order, not "(H, W)", and the "buffer width/height already allocated" comments on g8154/g8156 are the reverse as well. Also "the buffer's size changed" is true but the quantity is the pointer sprite's size.
- [ ] must-fix src/E1BB1.ASM:8-9: "allocates a new one sized through the indirect call [ds:80C6] plus 16 bytes" is wrong. The size is `si = [80C6](...) + 16` (1BB1:0076..0079), the largest free block must be at least `si` (1BB1:007B..0086), but the block allocated is `si - 16` (1BB1:0088..0094 `sub ax,16`, pushed as the low word of MemAlloc's size with high word 0 and flags 0, then `add sp,6`). So the buffer is exactly the result of [80C6], and the 16 bytes are only a margin required of the free memory (probably heap overhead [H]). Say that.
- [ ] should src/E1BB1.ASM:2 (name): `_f1BB1_0002` is a placeholder, which is acceptable, but the evidence above would support a name such as `SetMousePointerShape(hotX, hotY, shape)` with the claim recorded in the comment (hot-spot offset, shape record far pointer, hides the pointer with 1BBE:0002 and shows it with 1BBE:00ED around the change, reallocates the save-under buffer). Parameters are at [bp+6], [bp+8], [bp+0Ah/0Ch] (x, y, far pointer). Unit-level R2 will otherwise keep reporting it (`make readability UNIT=e1bb1`: 1 finding, in the baseline).
- [ ] should src/E1BB1.ASM (failure path): no `QUIRK 1BB1:xxxx:` markers, and the unit has two behaviours a port must keep. (1) When the allocation fails (`failed:` at 1BB1:00C6) the old buffer was already freed at `resize:` (1BB1:0052..005C) but ds:816A/816C are not cleared and ds:8154/8156 already hold the new size, so a later call with the same size passes `je ready` with a dangling buffer pointer. A first-time failure (816C == 0) leaves 816C zero and the next call retries. (2) The failure path also skips 1BBE:00ED, so the hide done by 1BBE:0002 (which increments ds:8146, 1BBE:00E0) is never undone; the pointer stays hidden until something else balances it. Both leave the semaphore released (`release:` runs). Mark them QUIRK.
- [ ] should src/E1BB1.ASM:11: "tells 1BBE:0002" is vague. 1BBE:0002 is the hide step: it does nothing when ds:814A is set or the hide count ds:8146 is nonzero, otherwise restores the saved background through [804E] (using the old buffer and sizes, which is why it runs before the globals are overwritten), then increments ds:8146. 1BBE:00ED is the matching show (decrements ds:8146 and, at zero, copies the position to 815C/815E, saves the background through [80AE] and draws through [80C2]). Say so, and say that the order (hide, store new shape, resize, show) is what keeps the old buffer valid. These are [H]-free (read from the bytes above) but the names of the indirect functions stay unknown.
- [ ] should src/E1BB1.ASM:12-13: "[ds:80AA] on the far pointer ds:8172/8174 ... [ds:80A2]" is correct as code, but the same pair brackets every pointer redraw (1BBE:029F..02B2, 1BBE:02E9..02FC, 1BBE:0315..0328, E1BF3:000E), so it is a fixed prologue/epilogue around drawing (the far pointer argument is passed to 80AA, nothing else is known). Nobody in this unit or in E1BF3 writes ds:8172/8174; say that the writer is unknown rather than "far pointer argument". Agrees with the single-far-pointer wording the E1BF3 review asked for.
- [ ] note The ds:812E semaphore here (1BB1:0008..000F, spin without a timeout, `inc` to take, `dec` to release) is the same one E1BF3 and 1BBE:01FE/02C2/0307 take, which is right; the comment ("0 = free (busy-wait acquire)") is accurate. A caller already holding it would hang; leave as is.
- [ ] note The decision that this is hand-written assembly (push dx/si/es after the frame, 1BB1:0002..0007) and the `ASSUME CS:NOTHING` explanation hold up; the 00 byte at 1BB1:0001 is the unit's marker, as in 1990:0001 and 1BF3:000D. The caller list is right: 07A9:010C (Level07A9) and ovl2:0000. ds:814A (checked by Level07A9 before the call, E07A9.C:82) is also tested by 1BBE:0002/00ED; it plausibly means "pointer disabled or no mouse" [H], and Level07A9 skipping the call when it is set is consistent with that.
- [ ] note Do not "fix" the unsigned loads: height (byte +3) is zero-extended with `xor ah,ah` and width is `byte + 2` plus 1 (zero-extended `xor dh,dh`, then `inc dx`), so a stored byte of 0 means 1 unit; the file header's "unsigned char counts" holds, only the names of the two fields are swapped (see the second must-fix).

## Summary

The code is described accurately line by line (semaphore, size comparison, free, size query, free-memory check, allocation, bracketing calls, return value), but the unit's meaning is misread: the header, the EXTRN comments and the "level" and "name record" wording all describe a level view buffer, while the neighbouring unit 1BBE (and E1BF3) show it is the mouse pointer: a hot-spot offset (8158/815A), a shape record (816E/8170) and a save-under buffer (816A/816C) sized from the sprite's height and width in 8-pixel units. Width and height are swapped, and the allocation size is misdescribed (the 16 bytes are a free-memory margin, not part of the block). Three must-fix items: the review fails until a decompiler corrects the header and the global comments (the function name may stay a placeholder, but `Purpose unknown:` or the pointer reading should be stated) and the allocation sentence. The unit is small and matches (208 bytes); no source change is needed for bytes.
