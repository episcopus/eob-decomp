## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E1BB1.ASM:5-7: the header says the caller passes a hot-spot offset and a shape record "both taken from gNamesDDE4[n]". Only the record comes from the table. The caller passes the literal hot spot (8, 8) when n > 0 and (0, 0) otherwise, and the record gNamesDDE4[n] in both cases (src/E07A9.C:91-94). Say that (for example "hot spot (8,8) or (0,0) by whether the caller's n is above 0; record gNamesDDE4[n]").
- [ ] must-fix src/E1BB1.ASM:14-17: "Both are unsigned char counts, so a stored 0 means 1" is wrong for the height. Byte +3 goes into the height unchanged (1BB1:0034, src/E1BB1.ASM:91, no +1); only the width gets the +1 (1BB1:003E, `inc dx` at src/E1BB1.ASM:94). A stored height of 0 is 0 pixels. Keep the +1 for the width only.
- [ ] must-fix src/E1BB1.ASM:24-26: "1BBE:0002 does nothing when ds:814A is set or the hide count ds:8146 is nonzero" is wrong for the count. With ds:8146 nonzero, 1BBE:0010 jumps to 1BBE:0075, which jumps to 1BBE:00E0, and that increments ds:8146 (a nested hide) and returns without restoring the background. It also does nothing when the count is 0 and ds:816C is 0 (1BBE:0017, 1BBE:000D). Evidence: `tools/re/disasm.py eob/EOB.EXE 1BBE` at 1BBE:0006..0017, 0075, 00E0. Correct it to: does nothing when ds:814A is set; when the count is nonzero only increments it; when the count is 0 and there is no buffer does nothing; otherwise restores the background and increments ds:8146.
- [ ] should src/E1BB1.ASM:18-20: "a margin, probably heap overhead [H]" ignores that LargestFreeBlock already takes 16 off (src/E19BC.C:142, `max -= 0x10`, and its header "less one 16 byte block"). So the caller's +16 is on top of the callee's -16: a raw free block of result + 32 is what passes. State both 16s, and drop the heap-overhead guess or keep it tagged [H] with that arithmetic.
- [ ] should src/E1BB1.ASM:27-29: "Around the change (and every pointer redraw) the pair [ds:80AA] ... and [ds:80A2] brackets the work" is loose. In 1BB1:00A9..00BD the pair brackets only the show call 1BBE:00ED (src/E1BB1.ASM:142-149). The resize and the 1BBE:0002 hide are outside it. Say "brackets the show call at 1BB1:00B8".
- [ ] should src/E1BB1.ASM:157-159 (second QUIRK 1BB1:00C6): "the hide done by 1BBE:0002 (which incremented ds:8146) is never undone" holds only when ds:816C was nonzero on entry (1BB1:0013). When there is no buffer, 1BBE:0017 returns before the increment, so the first-time failure case (the first QUIRK) leaks nothing. Say "when ds:816C was nonzero when 1BBE:0002 was called".
- [ ] should src/E1BB1.ASM:31 and :39: the word ds:812E is "semaphore" here and "busy flag" in src/E1BF3.ASM:7, 71 and 92. Use one term in both files. "Busy flag" is the accurate one: the acquire is a test and then an increment, not an atomic operation (see the note below). The global has no entry in re/globals.toml; a `make rename` to a name in both files would settle it.
- [ ] should src/E1BB1.ASM:33-34: "The unit is hand-written assembly (the compiler's C functions never push dx/es after the frame ...)" is stated as fact, but the top of the header says "kind asm [H] by the map". The c_like test (tools/re/map_units.py:42-46) looks only at the first three instructions after the frame, so "never" overstates it. Say "[H]: the map's c_like test finds no C-like frame here".
- [ ] should src/E1BB1.ASM:91 and :93 (`es:[si+3]`, `es:[si+2]`): the record offsets are bare numbers. Rule 4 of docs/process/READABILITY.md asks for named constants or a struct for offsets into records. The header carries the meaning, so this is a clarity item: for example `SHAPE_WIDTH8_BYTE EQU 2` and `SHAPE_HEIGHT_BYTE EQU 3` in the header, with the same meaning in the comments.
- [ ] should src/E07A9.C:47 (not this file; the owner of e07a9 should take it): the prototype `void SetMousePointerShape(int a, int b, void far *name)` has placeholder parameter names. This unit's evidence gives them hot-spot x, hot-spot y and the shape record (src/E1BB1.ASM:42-43, 46-47 and the function comment). The name `name` is also wrong: work/reviews/e07a9.md:15 says the table holds item icon images, so the parameter is an icon or shape record.
- [ ] should re/renames.toml:163 (the WHY of SetMousePointerShape, not in src/): "(8,8) for the sprite centre" is an inference. The code only subtracts the hot spot from the drawn position. Mark it [H], or say "(8,8) is the centre of a 16 by 16 cell if the record is 16 by 16 (e07a9 review)".
- [ ] note src/E1BB1.ASM:31: the acquire is not atomic: `cmp [812E],0 / jne / inc [812E]` can be split by an interrupt. If the mouse handler (1A72, whitepaper section "Mouse") runs in the gap and calls these routines, both take the flag [H]. This is how the original is; keep it, and do not "fix" it. The comment could say "busy flag, not a lock".
- [ ] note The name SetMousePointerShape has enough evidence: the function writes the hot spot (ds:8158/815A), the shape record (ds:816E/8170) and the save-under buffer, and 1BBE:00ED draws from the record (1BBE:01E8..01F4). The whitepaper says the game draws its own pointer (docs/design/WHITEPAPER.md:124). The caller in e07a9 passes item icon images (work/reviews/e07a9.md); that a carried item is shown on the pointer is [H]. "Mouse" here means the game's own pointer, which the INT 33h handler moves (docs/design/WHITEPAPER.md:124), not the driver itself.
- [ ] note The EXTRN names `_f1BBE_0002` and `_f1BBE_00ED` (src/E1BB1.ASM:59-60) are placeholders for unit 1BBE, which is not lifted yet. Their header comments say what they do (hide, show). When 1BBE is lifted, rename them to the names it earns (for example HidePointer and ShowPointer), and E1BF3.ASM and this file follow with `make rename`.
- [ ] note The globals ds:80AA, ds:80A2, ds:80C6 and the pair ds:8172/8174 stay placeholders: their EXTRN comments say what is known (the arguments, that the writer of 8172/8174 is unknown). That is the right level; nothing in 1BB1, 1BBE or E1BF3 writes 8172/8174 (checked in the full 1BBE disassembly: every use is a push).

## Summary

The unit is understandable from its source alone. It holds one function, SetMousePointerShape (1BB1:0002, 207 bytes), with the start marker byte at 1BB1:0001. The function hides the mouse pointer through 1BBE:0002, sets the hot spot and the shape record, resizes the save-under buffer when the sprite size changed (freeing the old buffer, asking [ds:80C6] for the size, then MemAlloc), and shows the pointer again through 1BBE:00ED. The name and the overall structure check out against the bytes, the callers (src/E07A9.C:91-94, src/EOV2.C), the 1BBE disassembly, the E19BC allocator signatures and the E1BF3 readers. Three claims are wrong and must be fixed: who passes the hot spot (the header says it comes from the table), the height rule (only the width gets +1), and what 1BBE:0002 does when the hide count is nonzero (it increments it). The rest are wording: the margin arithmetic, the scope of the 80AA/80A2 pair, the QUIRK condition, the semaphore and busy flag terms, the [H] tag on the assembly kind, and the record offsets. Placeholders left on purpose: g812E (no evidence beyond the flag use), g80AA, g80A2, g80C6, g8172, g8174 (their behaviour is not known individually), and _f1BBE_0002 and _f1BBE_00ED (unit 1BBE not lifted yet).
