## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E19F3.C:18: the name `ClipDrawRect` says the routine draws, and nothing in the unit or its callers shows a draw. The target `ds:8052` is unidentified, and the header itself says "a drawing or copy request". Evidence: the neighbouring pointer `ds:8046` is called by `19EC:002A` with two page segments from the table (src/E19EC.C:29-35), and both known callers pass two origins and an extent (082C:05DD, 0EF3:071E). What the bytes show is the clipping (origins moved to 0, size caps, two early returns). Rename to `ClipRect` (`make rename OLD=ClipDrawRect NEW=ClipRect WHY="clips a rectangle request before ds:8052; no draw shown"`), and change the header to "a rectangle request" in place of "a drawing or copy request".
- [ ] should src/E19F3.C:1-2: the header says "What 40 and 200 measure ... still unknown". src/E1A29.C:1-19 answers it. The region table at ds:009F holds the left edge and width in 8-pixel columns, and the top and height in lines. Record 0 is `0,0,40,200`, the full screen, and 082C:05DD passes exactly e=40, f=200. So e is a width in 8-pixel columns (cap 40, i.e. 320 pixels), f a height in lines (cap 200), and a and c are x origins in columns while b and d are y origins in lines, by the same convention. Say so in the header and cite src/E1A29.C.
- [ ] should src/E19F3.C:18 (R3): no comment of 8 words or more with the address 19F3:000E directly above the definition (`make readability UNIT=e19f3`: R3, listed in work/readability-baseline.txt). The description sits in the file header. Add a short comment right above `ClipRect` that says what it does (clips, then calls ds:8052), what the eight parameters mean, and the two early returns.
- [ ] should src/E19F3.C:18 (R4): the parameters are single letters. The evidence supports role names for a to f: a and c are x origins, b and d are y origins, e is a width and f a height (see the header finding; the callers push a=b=c=d=0, e=40, f=200 at 082C:05DD and a=b=c=d=0, e=22, f=120 at 0EF3:071E). For example `x1, y1, x2, y2, width, height`. g and h have no evidence beyond the caller values (g=2, h=0 at 082C:05DD; g=0, h=2 at 0EF3:071E) and nothing reads them: name them for what is known, and keep "passed through untouched" in the comment.
- [ ] note Types: `int` is right for all eight. Every compare in the bytes is signed (`jle` and `jge` at 19F3:0019..0068), so `unsigned` would be wrong.
- [ ] note Call-site count: the earlier round said 29 callers (22 in overlays). `build/packets/e19f3.md` lists 30: 7 resident and 23 in overlays. The header does not cite a count, so nothing in the source needs changing.
- [ ] note `gFar8052` (ds:8052) and `gHandler8046` (ds:8046, src/E19EC.C) are two placeholders for far pointers in the same driver table, in different styles. `gDrawLine` (ds:8062, src/E1A1F.C) is named for what it does. Harmonise these in Phase 6, not here.

## Summary

The unit is short, its code is easy to follow, and the earlier must-fix items are fixed. It is not yet
understandable from its name alone: `ClipDrawRect` claims a draw that no evidence shows, and the header
calls 40 and 200 unknown although src/E1A29.C gives their meaning (8-pixel columns and lines). The
parameters a to h are placeholders with no role names, and the function has no comment of its own above
its definition. The a to f names are supported by the caller values and E1A29; g and h stay placeholders.
Review fails on the name; with the rename and the header change it should pass on a second review.
