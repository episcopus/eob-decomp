## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E19F3.C:13: "the pixel arguments of gRect806A" names a routine that is no longer called that. The ds:806A routine is `gFillRect`: re/renames.toml:860-865 renames `ds:806A=gFillRect` and says so ("not the address-suffix placeholder gRect806A"), and src/E1DE7.C:62, src/E082C.C:39 and src/EOV2.C:163 all declare it as gFillRect. Fix: write gFillRect in that sentence.

- [ ] must-fix src/E19F3.C:54-58: "The only src/ call whose two y origins differ is 1DE7:03B2" and "Every other src/ call with named origins passes x1 = x2 and y1 = y2 (EOV6.C:376, :385, :481)" are false as written. src/E082C.C:113 is `ClipRect(x - 1, y, 0, 0xbf, ...)`, so y1 = y and y2 = 0xbf differ; src/E082C.C:209 is `ClipRect(0, 0xbf, x - 1, y, ...)`, the same y pair in the other order. The disassembly agrees: the pushes at 082C:006D and 082C:038A give y1 = [bp+c], y2 = 191 and y1 = 191, y2 = [bp+c] (the header's own lines 59-61 say so). Fix: name all three calls whose y origins differ (1DE7:03B2, 082C:006D, 082C:038A) and say the x1 = x2, y1 = y2 pattern holds for EOV6.C:376, :385, :481 (and the literal zeros of EOV2.C:365 and the 082C:05DD and 0EF3 calls). The 1DE7:03B2 lead is still a lead, not evidence, and should stay tagged [H].

- [ ] should src/E19F3.C:77: "The load image holds 00 00 00 00 here, so it is zero in the file" gives no address. Evidence I checked: DGROUP is paragraph 0x212E (the default of tools/re/disasm.py); the MZ header is 0x2800 bytes; the load module is 0x31350 bytes (from the MZ page fields); so ds:8052 is file offset 0x2800 + 0x212E0 + 0x8052 = 0x2BB32, inside the load module, and the 8 bytes there are zero. Cite 0x2BB32 and the DGROUP base in the comment, and say the base is the disassembler's default (a [H] until the startup code that sets DS is cited).

- [ ] should src/E19F3.C:79: "no setter found" has no search behind it. A byte scan of eob/EOB.EXE and build/re/eob-overlays/*.bin for direct-addressed writes to offset 0x8052 (`89` with modrm 00/reg/110, `a3`, `c7 06`, `c6 06`, each followed by `52 80`) finds none. The scan does not cover indirect or segment-override writes. Fix: say "no direct write to ds:8052 in EOB.EXE or the overlay binaries (a byte scan, indirect writes not searched)" so the next reader knows what was checked.

- [ ] should src/E19F3.C:94: "an origin below SCREEN_COLUMNS passes with any width" is looser than the code. The width is capped at SCREEN_COLUMNS (line 97), and a negative width passes unchanged (QUIRK 19F3:0036, 004B, 005C, 0070 in the header). Say "with any width up to SCREEN_COLUMNS, and a negative width unchanged".

- [ ] note src/E19F3.C:1-64: the file header is 64 lines for a 137-byte function. The summary (lines 1-3) is clear and every trace I checked is right, but a reader has to get through the caller survey and the ds:8052 evidence before the quirk traces. Consider moving the caller survey and the pointer evidence to a short "evidence" block below the quirk list, or to the whitepaper, when the header is next edited.

- [ ] note src/E19F3.C:73-74: SCREEN_COLUMNS and SCREEN_LINES are local to this file. The other units pass literal 40 and 200 for the same full-screen rectangle: src/E082C.C:280 and :285, and src/EOV2.C:365 (0x28, 0xc8). Owners of those units could use the same constants once a shared place for them exists. Not blocking.

- [ ] note src/E19F3.C:95: the name ClipRect is fair for what the function does to origins and sizes (negative origins raised to 0, origins at or past SCREEN_COLUMNS rejected, sizes capped). It claims a bit more than the code does: the header says the far edge x1 + width is not clipped. The name is used across src/, so a change would be the supervisor's call. Not blocking.

- [ ] note tools/agent/packet.py `known_names()` (line 92, regex on line 101): still open from round 6. For a function-pointer declaration (`extern void (far *gFar8052)(int x1, ...)`) it takes the first parameter as the name, so build/packets/e19f3.md lists "ds:8052 x1 (E19F3.C)". Same bug for gDraw80C2 in E1A29.C. Routed to the supervisor: tools/agent/ is outside what a reviewer may change. Not a fault in src/E19F3.C.

## Summary

The unit is understandable from its source alone. ClipRect does what the code shows: the disassembly at 19F3:000E to 19F3:0096 agrees with each branch (the width and height caps, the negative-origin shifts with their partner origin and size, the x1 and x2 returns at 19F3:003B and 19F3:0040, the unchecked x1 rewrite at 19F3:0045 that the quirk describes, the push order, and the indirect call through ds:8052 at 19F3:008C). The names are evidenced or honest: SCREEN_COLUMNS and SCREEN_LINES match the region table in src/E1A29.C and the screen bounds in src/E1A72.ASM, the region record 0x23B7F is 0,0,40,200, and gFar8052, extra1 and extra2 are placeholders that say they are. The two must-fix items are a stale routine name (gRect806A, now gFillRect) and a false statement about which caller calls pass origins in different pairs. Both are one-line fixes in the header. The should items sharpen evidence the header already claims.
