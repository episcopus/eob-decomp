## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E19F3.C:54-55: "1DE7:03B2 (E1DE7.C:245)" gives the function's entry as the address of a call. The only `lcall 19F3:000E` in DrawTextLine is at 1DE7:0474 (disassembly of 1DE7; pushes at 1DE7:0450 to 0470), which is where the call stands in E1DE7.C:245. 1DE7:03B2 is the entry of DrawTextLine (E1DE7.C:232). The other two differing-y calls are given their call-site pushes (082C:0062/005B, 082C:0378/0383), so this one should be too. Fix: cite 1DE7:0474 (pushes 1DE7:0450 to 0470) as the call site and keep 1DE7:03B2 only as the name of the function it sits in.
- [ ] must-fix src/E19F3.C:11-12: "E1DE7.C:245-248 and EOV6.C:375-376 pass gTextLeft, gTextTop, gTextWidth and gTextHeight unshifted to ClipRect" is wrong for E1DE7.C:245, which passes `line` as the height, where `line = (gTextHeight / gFontHeight1A47 - 1) * gFontHeight1A47` (E1DE7.C:244), not gTextHeight. Only EOV6.C:376 and :481 pass gTextHeight itself. Fix: say that E1DE7.C:245 passes the whole-line height `line` derived from gTextHeight, and name EOV6.C:376 and :481 as the callers that pass gTextHeight unshifted. The x-column reading the sentence supports still holds on gTextLeft, gTextTop and gTextWidth.
- [ ] should src/E19F3.C:80-83: "The load image holds 00 00 00 00 here" is right for the far pointer (4 bytes), but "the 8 bytes there are zero" then reads as if the pointer were 8 bytes. The eight zero bytes at file offset 0x2BB32 are ds:8052 to ds:8059: the pointer and the four bytes after it. Say that. Also "the 0x31350-byte load module" is the load image after the MZ header: it runs from file offset 0x2800 to 0x33B4F (the header's 0x2800 plus 0x31350 is 0x33B50, the end of the MZ load module by the e_cp and e_cblp fields). Say "the 0x31350-byte load image that starts at the 0x2800-byte header" so a reader does not count the header twice. Evidence checked: MZ fields and the zero bytes at 0x2BB32. The region record at 0x23B7F (`00 00 00 00 28 00 c8 00`) is consistent with the same DGROUP base 0x212E, which is some support for the [H] base, not proof.
- [ ] should src/E19F3.C:4-6: "The width is read as the shared extent of the x origin pair [H]" does not say what the bytes do, and "shared extent" is not defined anywhere in the header. What the code shows (19F3:0036 for x1, 19F3:004B for x2): when an origin is raised to 0, the width moves by that origin's amount, so x1 + width (the far edge) stays where it was. Say that, and keep the columns reading as the [H].
- [ ] should src/E19F3.C:116-120: the QUIRK for the x2 shift (QUIRK 19F3:0045: x1 is rewritten after both x tests, so an origin past SCREEN_COLUMNS can reach the far routine) is marked only in the 68-line header. A one-line `QUIRK 19F3:0045:` pointer above the x2 shift would put the mark where the behaviour is, which is where a porter reads the code. The header keeps the example.
- [ ] note src/E19F3.C:77-93: the extras. E082C.C:279 and :284 pass `extra1` equal to the mode given to 19EC:002A in both LoadScreenImage cases (mode 4 with extras 4,2; mode 2 with extras 2,0). That is a lead that extra1 is a driver mode, not evidence: the other call sites (E082C.C:113 with 0,2; E082C.C:209 with 2,0; E1DE7.C:245 with g8115 twice) do not fit it, so the placeholder names stay. Worth one line in the header, tagged [H], so the next reader can test it against the far routine.
- [ ] note src/E19F3.C:93: gFar8052 is the only declaration of ds:8052 in src/ (re/symbols.toml has no other entry for it), so the name is free to change without a rename across files. It is a placeholder with its evidence stated in the header, which is the right state for it.

## Summary

The unit is understandable from its source alone. The function body is plain and each branch in it matches the disassembly: the width and height caps (19F3:0019 to 002B), the x1 and y1 shifts with their partner origin and size (19F3:0030 to 0039 and 0050 to 005F), the x tests at 19F3:003B and 0040, the x2 and y2 shifts (19F3:0045 to 004E and 0064 to 0073), the push order (extra2 first, x1 last) and the indirect call through ds:8052 at 19F3:008C. ClipRect is what the code does, and the SCREEN_COLUMNS and SCREEN_LINES constants rest on evidence I checked (the region record at 0x23B7F, the screen bounds set at E1A72.ASM:191-192, the 40x200 clip at E1BBE.ASM:79). gFar8052, extra1 and extra2 are placeholders that say so. The two must-fix items are both wrong citations in the header, not in the code: a call address (1DE7:03B2 for the call at 1DE7:0474) and the height argument at E1DE7.C:245 (`line`, not gTextHeight). Both are comment-only fixes. The shoulds and the note sharpen evidence the header already claims.
