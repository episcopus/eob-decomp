## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] should src/E19F3.C:119 to 120: the function comment ends "and a negative width unchanged (x1 = 30, width = 40 passes)". "a negative width unchanged" has no verb, and the parenthetical example shows only the first clause. The negative-width case is the header's own example (src/E19F3.C:30 to 32: ClipRect(-30, 0, 0, 0, 20, 200, 0, 0) passes width -10). Fix: "...passes with any width up to SCREEN_COLUMNS (x1 = 30, width = 40 passes), and a negative width passes unchanged (ClipRect(-30, 0, 0, 0, 20, 200, 0, 0) passes width -10)."
- [ ] should src/E19F3.C:121 and re/renames.toml:437 to 442: the name `ClipRect` says the rectangle is clipped. The function clips the two origins into the screen and caps the sizes; it does not clip the far edge x1 + width. The header's own examples show a far edge past the screen (src/E19F3.C:16: x1 = 30, width = 40 passes unclipped; src/E19F3.C:25 to 27: ClipRect(0, 0, -50, 0, 40, 200, 0, 0) passes x1 = 50 and width -10). The rename's `why` ("clips a rectangle request before ds:8052; no draw is shown") does not say which part is clipped. The callers use the name as "clip" (E082C.C:269, EOV6.C:358, E1DE7.C:228), and it is used at more than a dozen call sites in src/, so a rename is a cross-file change, not a unit edit. Options: keep the name and make the `why` say "clips the origins and caps the sizes; the far edge is not clipped", or leave the name choice to the human in phase 6. Not a must-fix: the origin clip is real and the header states the gap.
- [ ] should src/E19F3.C:63 to 64: "(a one-line scroll is the [H] reading of the source and destination pattern, lines 66 to 67)" names no file, so a reader cannot tell the lines are in this file. They are: src/E19F3.C:66 to 67 hold the "1DE7:0474 reading fits x1, y1 as a source ..." sentence. Fix: write "E19F3.C:66 to 67" in the sentence.
- [ ] note (routed; not a finding on this unit, for the e082c reviewer and the owners of e0bd2 and e1bbe): E082C.C:91 says the field "is saved and restored with ClipRect", and E082C.C:207 calls 082C:0062 "the save". This unit cannot show it from its own bytes, so the question stays open; no change is asked of this file.

## Summary

The unit is understandable from its source alone. Every branch of the function matches the disassembly I read: the width and height caps, the signed compares, the origin shifts and their partner moves, the push order and the call through ds:8052. The worked examples in the header give the stated values when run through the code, and the caller arguments I checked (the DrawTextLine call, the two y-origin calls, the extras pairs and the byte-only 0EF3:24F3 call) match what the header says. Names: `ClipRect` is backed by what the function does to the origins and sizes and is the name every caller uses, but it overstates the far edge (should, above). `gFn8052` follows the `gFn<address>` pattern for far pointers of unknown purpose; its target is not traced, so it stays a placeholder. x1 to y2, extra1 and extra2 are placeholders whose evidence the header states. width and height rest on region record 0 (re/renames.toml:82, 0,0,40,200) and the screen bounds (src/E1A72.ASM:191-192). No must-fix, and nothing here is a matcher or spec question, so there is no escalation.
