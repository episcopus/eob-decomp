## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E19F3.C:32-33: "so the bottom 9 lines are copied" states what the far routine does. The
  same header says that routine is not traced ("What the far routine does is still unknown"), and no byte
  says it copies anything. The evidence supports only the geometry: 082C:006D pushes y2 = 191 with height 9,
  so the rectangle covers lines 191 to 199 (191 + 9 = 200). Say that the rectangle covers the bottom nine
  lines, not that they are copied.

- [ ] should src/E19F3.C:32-34: the 082C:038A clause is vague, and its y reading conflicts with the evidence
  offered. The pushes at 082C:0366..038A are extra2 = 0, extra1 = 2, height = 9, width = [bp+e] + 2,
  y2 = [bp+c], x2 = [bp+a] - 1, y1 = 0xbf (191), x1 = 0. So 038A puts 191 in y1, while 082C:006D puts it in
  y2. The "y2 as a destination origin" reading rests on 006D alone, and 038A goes the other way. Give the
  038A values as the 006D clause does, and say the callers disagree on which origin holds 191.

- [ ] should src/E19F3.C:9-11 and 18-19: the header does not say what the function passes on after the
  negative-x2 shift. That shift runs after the x1 test (19F3:003B `cmp di,28h`): 19F3:0045..004E
  (`or si,si; jge; sub di,si; add [bp+0Eh],si; xor si,si`) adds -x2 to x1 and to nothing else, and no test
  sees x1 again. So ClipRect(0, 0, -50, 0, 40, 200, 0, 0) passes x1 = 50 and width = -10 to the far routine.
  A negative x1 gives the same result on its side: ClipRect(-30, 0, 0, 0, 20, 200, 0, 0) passes x2 = 30 and
  width = -10. Also the example "(x1 = 30, width = 40 passes unclipped)" should say that nothing clips the far
  edge x1 + width. Mark the behaviour `QUIRK 19F3:0045:` with these results (READABILITY, comments rule), or
  state why it is intended.

- [ ] should src/E19F3.C:36-39: the screen-limit comment cites src/E1A72.ASM:176, a prose comment. The code
  that sets the bounds is src/E1A72.ASM:191-192 (`mov [g814E],13Fh` and `mov [g8152],0C7h`, that is 319 and
  199, the screen width and height minus one; declared at E1A72.ASM:45-46). Cite those lines. The column
  reading is also supported by src/E1BBE.ASM:79 ("8-pixel columns ... clipped to the 40x200 screen") and by
  src/E1A29.C (x in 8-pixel columns, gRegionLeftPx = left * 8).

- [ ] note src/E19F3.C:4-8: the first sentence states the units as the region table's, and only line 8 says
  the reading is an inference [H]. Nothing in the bytes gives the units. The [H] tag is honest; the next
  reader should see it at the first claim too.

- [ ] note correction to the previous round's note (`work/reviews/e19f3.md` before this file): the
  extra1/extra2 pairs at 082C:006D are (extra1, extra2) = (0, 2), not (2, 0). The bytes push 2 first

## Summary

The unit is understandable from its source alone. ClipRect names what the bytes do: it clips the origins
to 0 with their partners and the size, caps the size, and returns early for an x origin at or past
SCREEN_COLUMNS. The signature, the push order (extra2, extra1, height, width, y2, x2, y1, x1) and the caller
values I checked (082C:006D, 082C:038A, 082C:05DD, 0EF3:071E, 0EF3:0860) match the header, except the 038A
clause, which is vague and misleading about y. The extra pair for 006D in the previous round's note was wrong;
the source does not state it, so no change. The one must-fix is a claim that the untraced far routine copies the
bottom nine lines. The shoulds are the 038A description, a QUIRK for the negative-x2 path (x1 and width are not
re-tested after that shift), and the screen-bound evidence (E1A72.ASM:191-192). Placeholders left: extra1 and
extra2 (their roles are unknown and the header says so) and gFar8052 (named from its address, with no evidence
for a purpose). Those are honest; no change needed for them.
