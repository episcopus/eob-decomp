## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E19F3.C:60-64: "since a zero would trap" is a claim with no evidence, and probably wrong. The image
  holds 00 00 00 00 at 212E:8052 (checked), and 19F3:008C `lcall [0x8052]` calls through it. A far call to 0000:0000
  runs the bytes of the interrupt vector table at linear 0, not a defined routine; nothing here shows a trap (no oracle
  run, no source). Say what the bytes show: a zero pointer makes the call go to 0000:0000, the interrupt vector table
  [H]; keep "must be set before 19F3:008C calls through it" as the inference it is, and drop "would trap".

- [ ] should src/E19F3.C:32-33: "The eight ints then go on unchanged in source order" contradicts the adjustments just
  above (the origins and sizes are changed). Say "are passed on in source order"; the push order that follows is right

- [ ] should src/E19F3.C:3-4: "x1 and x2 are two x origins sharing the width as their extent" (and the y pair with the
  height) is a reading stated as fact. The bytes show that the width moves with whichever origin is raised

## Summary

The unit is understandable from its source alone. ClipRect does what its code shows: it caps the width and height,
raises a negative origin to 0 with its partner origin and the size, and returns early when an x origin reaches
SCREEN_COLUMNS. Every byte-level claim I checked is right. The one must-fix is a claim with no evidence, "a zero would
trap" for the function pointer at ds:8052: a far call to 0000:0000 is not a defined trap, and the header should say only
what the bytes show. The shoulds are a wording slip ("go on unchanged"), one reading stated as fact (the "extent" of
the origin pairs), the raw "[8102]" where the rest of src/ says g8102, the first QUIRK example's width, the far edge
the function comment does not mention, and the length of the unit comment. The placeholders are honest: gFar8052 is
named from its type and address, and extra1 and extra2 are named by position with their roles marked unknown.
