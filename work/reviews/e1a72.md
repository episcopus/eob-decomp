## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [ ] must-fix src/E1A72.ASM:44, :236 (and src/E07C8.C:37): gMouseDisabled is described as "0 disables" and "With DGROUP:814A zero it does nothing". The polarity is reversed. The handler tests `cmp [814A],0; jne` and leaves at once when the word is nonzero (1A72:0185-018A, `jne 0x1e9` to the exit; re/globals.toml:302 says the same). MouseInit sets it to 1 before it installs the handler (line 215), so nonzero means disabled. E07A9.C:105, E0BD2.C:98, E0ACD.C:111 and E0D1C.C:110 all say "nonzero disables". E07C8.C:37 carries the same wrong text; its owner should fix that line too.
- [ ] must-fix src/E1A72.ASM:173-174 (MouseInit comment) and :41: the 640-wide test is reversed. The code stores 1 in DGROUP:8144 when the reset position x is NOT 0A0h (lines 206-211: `cmp cx,0A0h; je L0144; mov [g8144],1`), so the driver counts as 640 wide when it reports x other than 160. The comment says "when the driver reports x = 0A0h, records 640 wide mode". Also `shl cx,1` (line 218) doubles the constant centre 0A0h, not the reported x. Fix both sentences. The g8144 comment at line 41 should state the test (reset x not 0A0h) instead of "reports a 640 wide range", which is an inference.
- [ ] must-fix src/E1A72.ASM:34 and :238 (g8132 and the handler): "button bits or-ed into every event" and "It or-s in the mask" are wrong. The mask is or-ed in only when g8132 is nonzero AND the middle-button bit (BX bit 2, value 4) is set, and then the bit is replaced: `test bx,4; je; and bx,3; or bx,ax` (lines 264-270; disassembly 1A72:01A6-01B6). Say that, with the condition.
- [ ] must-fix src/E1A72.ASM:241-242 (handler, zone branch): "either redraws the tracking rectangle" does not describe the code. When 8160 bit 8000h is set and the position is in the zone, the handler calls g80AA with the far pointer, HidePointer (1BBE:0002), g80A2 and sets 4000h (lines 287-294; disassembly 1A72:01EC-0204). It draws no rectangle itself and does not call ShowPointer. The other branch (lines 318-324, 1A72:025C) hides, shows and then calls g80A2. Describe each branch by what it calls.
- [ ] must-fix src/E1A72.ASM:310-313 (the zone test, not mentioned in the comments): `cmp cx,[gZoneLeft]; jl L0250` jumps to the y test when x is LESS than the left edge, so the left edge is never checked. Only x > right (`jg L025C`) and y outside [top, bottom] leave the zone (disassembly 1A72:0244-025A confirms `jl 0x250` at 1A72:0248). The handler comment says the position is "inside DGROUP:8162..8168", which is wrong for the left edge. Mark this `QUIRK 1A72:0248:` (the test is as the original has it; a port must keep it) and say it in the handler comment. src/E1BBE.ASM:39, :202 and re/globals.toml:202 say the handler "tests the cursor against" the left edge; they should be told the same.
- [ ] must-fix src/E1A72.ASM:7, :32, :239, :361-362 (the busy flag): "semaphore" and "busy-wait acquire" describe a lock. The code tests then increments (MouseInRect 377-379 `cmp [812E],0; jne; inc`; the handler 284-295 tests and then sets 1). That is not atomic: the mouse handler is called by the driver, so it can run between the test and the increment, and both would think they hold the flag. re/globals.toml:297 and src/E1BB1.ASM:73 already say "busy flag, not a lock". Use "busy flag" in this file and drop "acquire" and "semaphore".
- [ ] must-fix src/E1A72.ASM:20: `_LocateOverlayFile` is described as "locates and opens the overlay file". src/E1C0E.C:778-800 shows that 1C0E:1310 opens the name (EOB.EXE, the program file, not an overlay) only to probe it, closes the probe at once and returns drive plus 1, or 0. It leaves no handle for the caller. Header line 12 ("(re)opens EOB.EXE through 1C0E:1310") and line 66 ("retries opening EOB.EXE through 1C0E:1310") say the same thing. The real open is the separate `_open` call (line 143, after a successful probe at lines 101-107). Fix all three.

- [ ] must-fix src/E1A72.ASM:23-24: `_HidePointer` and `_ShowPointer` are cited "(E1BB1.ASM)". They are defined in src/E1BBE.ASM:85 (1BBE:0002) and :174 (1BBE:00ED). E1BB1.ASM:118 defines `_SetMousePointerShape` at 1BB1:0002, a different function. Cite E1BBE.ASM.

## Summary

The unit is understandable from its source, and most names are evidenced: the INT 3Fh handler, the mouse setup and handler, the interrupt and far-pointer helpers, and the callers are all tied to addresses and to the other units. The problems are in what the comments say, not in the code. Four statements are wrong (the gMouseDisabled polarity, the 640-wide test, the middle-button mask, and the zone branch), the zone's left edge is not tested (a quirk the comments must mark), the busy flag is called a semaphore, and four citations point to the wrong unit or function (ShutdownGame, HidePointer, ShowPointer, LocateOverlayFile's behaviour) plus one wrong caller (StartupGame, not main). Names: `MouseInRect` should be a question name, and `MouseInit` is a noun-first name; the rest of the function names hold. Placeholder names (g80A2, g80AA, g80EC, g8104, g8111, g8026, g8028, g8130-g8144, g814E, g8152) are honest and need no change, but several of their comments should say what the code does, as above. `make match FILE=src/E1A72.ASM` reports 8 of 8 functions matching (841 bytes, unit complete) and `make readability UNIT=e1a72` reports 0 findings. No matcher or spec question: every finding is a comment or a name, so there is no escalation. Source not edited (reviewer).
