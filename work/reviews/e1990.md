## Findings

Each finding is a checkbox. `must-fix` blocks `make review-pass` until a decompiler ticks it off
(with the commit that fixes it); `should` and `note` do not block.

- [x] must-fix src/E1990.ASM:5-6: "main calls them when the graphics argument reduces to 1" names the wrong caller. The calls come from StartupGame (07C8:0199): CheckMemoryChain at 07C8:01BB and ReserveMemoryBelowVideo at 07C8:01F2, both in the case where the graphics argument has been reduced to 1 (src/E07C8.C:178 to 188). TrimMemoryToVideo is called from ShutdownGame at 07C8:060D, under `ds:8102 == 1` (07C8:0606; src/E07C8.C:343 to 344). Name StartupGame and ShutdownGame.

- [x] must-fix src/E1990.ASM:13-16 (gMemTopSeg): "its caller then stores the video top over it (07C8:0212)" is wrong. The caller stores `atol(gEnvPtr->number)` (src/E07C8.C:189; disassembly 07C8:01FA to 0212: `les bx,[8894]`, push the far pointer at +18h, call atol at 0000:5D63, `mov es:[2],ax`). ReserveMemoryBelowVideo's return value (the video top) is not stored there; it is the memtop argument to the page table at src/E07C8.C:220. Say what is stored: the end of DOS memory first (1990:01F0, E1990.ASM:248), then atol of the numeric string at gEnvPtr+18h (07C8:0212). What the string holds is Purpose unknown: nothing in src/ or docs/ writes ds:8894.

- [x] must-fix src/E1990.ASM:306-308 (TrimMemoryToVideo header): "to the segment ReserveMemoryBelowVideo left in gMemTopSeg (the video top)" is wrong twice. gMemTopSeg is not the video top: 1990:01F0 stores the segment just past the last block (E1990.ASM:245 to 248). And StartupGame overwrites it with atol(...) (07C8:0212) before the exit call at 07C8:060D runs TrimMemoryToVideo, so Trim uses the stored number, not the value Reserve left. Fix both.

- [x] must-fix src/E1990.ASM:21 (gMovedParas: "size in paragraphs of that block"): the stored value is the block size plus its own MCB paragraph. The code loads `es:[3]`, adds 1, and stores it at 1990:00D1 (E1990.ASM:111 to 113); the allocation then requests the size without the +1 (1990:00D6, E1990.ASM:114 to 115). ReserveMemoryBelowVideo depends on the footprint: gNewMemTopSeg = gVideoTopSeg - gMovedParas (E1990.ASM:258 to 260), and the copy loop moves `ds:[3]+1` paragraphs (1990:023F to 0243). Say "the block's size plus its MCB paragraph (its footprint)".

- [x] must-fix src/E1990.ASM:66-70 (CheckMemoryChain header): "grow and move it into the free block that follows" describes a step the code does not take. The copy is requested with the same size (1990:00D6 to 00D9, E1990.ASM:114 to 116), DOS chooses the block (first fit), PSP:002C is pointed at the copy (1990:00DD), and the old block is marked free by zeroing its owner (1990:0101, E1990.ASM:136). Write those steps instead; no growth, and no claim about which block DOS picks.

- [x] must-fix src/E1990.ASM:167-168 (ReserveMemoryBelowVideo header): "Argument (far, at bp+6) is the graphics mode" is not supported. The callee uses the argument as a count: `(n-1)` shifted by 11 paragraphs (1990:01A8 to 01B4, E1990.ASM:215 to 221), so it reserves (n-1) x 32 KB below the probed video top. The only caller passes the literal 3 (src/E07C8.C:188; `lcall 1990:0133` at 07C8:01F2), so the reserve is 64 KB and the argument is not a graphics mode. Describe the arithmetic and name the parameter (E07C8.C:83 calls it `n`). "far, at bp+6" should say the first word argument of a far call, at bp+6.

- [x] must-fix src/E1990.ASM:231 (ReserveMemoryBelowVideo) and :324 (TrimMemoryToVideo), each a QUIRK. When the probe block's type is not 'M' (1990:01C6 to 01CC, 1990:0294 to 0296), the code jumps to the common exit with the probe segment still pushed (1990:01C2 in Reserve, 1990:028A in Trim). The exit pops are then one word out: the far return pops the wrong words, and the probe block is not freed. The bytes match the original, so this is the original's behaviour, and rule 6 of READABILITY (quirks are marked) applies. Add `QUIRK 1990:01CE:` to ReserveMemoryBelowVideo and `QUIRK 1990:0296:` to TrimMemoryToVideo, with what happens (stack one word out, probe not freed, reached only when the probe block is the last block of the chain, which is not checked here; say "not checked" rather than guessing when).

- [x] should src/E1990.ASM:17-18 (gVideoTopSeg): "top segment of video memory found by ReserveMemoryBelowVideo, whose result it is" overstates. The value is the probed top (the segment where the B800 probe aliases, or A000) less (n-1) x 32 KB (1990:01B6, E1990.ASM:222), and it is raised to memtop + footprint when that fits (1990:0202 to 0207, E1990.ASM:252 to 254). - [x] should src/E1990.ASM:19-20 (gMovedSeg): "the environment block that CheckMemoryChain moved (its copy is released later)" is hard to follow. The value is the data segment DOS gave the relocated copy of the environment block (1990:00E0). ReserveMemoryBelowVideo copies that copy to its final place and frees it (1990:0268 to 026D, ES = gMovedSeg, INT 21h 49h). Say that.

- [x] should src/E1990.ASM:23 (gNewMemTopSeg): "new top of memory stored into PSP:0002" holds only when a block was moved (the store at 1990:0264 is on the path after the `gMovedSeg == 0` test at 1990:0231). Say "when a block was moved".

- [x] should src/E1990.ASM:165-168 (ReserveMemoryBelowVideo header): "shrink the free block so the program ends at that top" says the owner was checked. The header also leaves out the PSP updates (PSP:002C at 1990:025B, PSP:0002 at 1990:0264). Add both.

- [x] should src/E1990.ASM:66-70 (CheckMemoryChain header): "AX = 0 when the chain ends in a 'Z' block" is incomplete. The last step calls CheckMCB (1990:0110, E1990.ASM:140), so AX is CheckMCB's result after it has merged the free blocks, and the merge is a side effect the comment should name. The caller's test is at 07C8:01C0 (`or ax,ax`), not 07C8:01BB, which is the call; say "the test at 07C8:01C0 (src/E07C8.C:181)".

- [x] should src/E1990.ASM:24 (`mcbseg`): a global without the `g` prefix that READABILITY.md asks for (`gMcbSeg`). Rename with `make rename OLD=mcbseg NEW=gMcbSeg WHY="..."` (or the address 1990:000E). No other file declares it.

- [x] should src/E1990.ASM:22 (`db 0,0` at 1990:000A): nothing reads 1990:000A in this unit (no `cs:[0Ah]` in the disassembly). Say "unused (no reader in the unit)" so the bytes are not taken for data.

- [x] should src/E1990.ASM:1-7 ("the Tandy link is inferred"): name the evidence, so the name is not a guess. WHITEPAPER 2.6 (line 117) reads argv digit 1 as Tandy and 3 as VGA (the VGA branch clears A000:0000 at src/E07C8.C:192); START1's menu order is CGA, Tandy, EGA, VGA (WHITEPAPER line 105). - [x] note src/E1990.ASM:12 (`db 0` at 1990:0001): the same open question as work/reviews/e1bb1.md (AGENTS rule 2: a `db` byte in a unit that must match). The byte is the EXE's byte at 1990:0001 (0), a data byte with no reader, not code. Not decided here; the human answer applies to this unit too.

- [x] note src/E1990.ASM:139 (`mov word ptr cs:gVideoTopSeg,9800h`): a dead store. Every path overwrites it at 1990:01B6 before any read. Worth a comment ("overwritten before use"), since a reader will wonder what 9800h is.

## Summary

The four names are supported by the code: CheckMCB walks and merges the MCB chain, CheckMemoryChain relocates the environment block, ReserveMemoryBelowVideo reserves room below the probed video top, and TrimMemoryToVideo gives the last block back. The evidence is in the file (the 'M' and 'Z' block types, INT 21h 48h, 49h and 4Ah, PSP:002C, the callers in src/E07C8.C), and no name is a placeholder. The unit is not yet understandable from its source alone, because the header and four global or function comments misstate who calls the functions, what gMemTopSeg holds (the end of DOS memory, then a number from a string whose origin is unknown), the argument of ReserveMemoryBelowVideo (a count of 32 KB steps, not the graphics mode), the size kept in gMovedParas (one more than the block), and the copy step (the same size, not a growth). Two exit paths leave the stack one word out and carry no QUIRK mark. The matcher result (4 of 4) is not in question, and there is no matcher or spec question for the human: the stack behaviour is in the original bytes, so it is a quirk to mark, not a tool problem. `make readability UNIT=e1990` reports 0 findings, but its rules are for C; this is an ASM unit, so the findings above are the review.

### Findings

- [x] must-fix src/E1990.ASM:27-28 (gVideoTopSeg): "raises it to memtop plus the moved footprint when that fits" has the direction wrong. Round 1 wrote "raised" too; that was my error, and the decompiler took it over. At 1990:01F4 to 01F9 bx = gVideoTopSeg - gMovedParas. At 1990:01FE, `cmp ax,bx` compares memtop (ax, stored at 1990:01F0), and `ja` at 1990:0200 skips the add at 1990:0202 to 0207 when memtop is above bx. So the add runs only when memtop <= gVideoTopSeg - footprint, and then gVideoTopSeg = memtop + footprint, which is at most its old value. The top is lowered or left equal, never raised. Say that.
- [x] must-fix src/E1990.ASM:193 (ReserveMemoryBelowVideo header): "points PSP:002C at the moved block's MCB (1990:025B)" names the wrong value. PSP:002C gets the moved block's data segment, not its MCB: from 1990:0236 es = newtop (the copy's MCB, written 1990:0236 to 024C), 1990:0256 and 0258 set bx = es + 1, and 1990:025B stores bx at [002Ch]. That is the same kind of value CheckMemoryChain stores at 1990:00DD (AX from INT 21h AH=48h, the data segment). Say "the moved block's data segment (its MCB plus one)".
- [x] should src/E1990.ASM:37-38 (gMovedParas): "ReserveMemoryBelowVideo uses the footprint (1990:01F9, 1990:0243)" cites the wrong read. ReserveMemoryBelowVideo reads gMovedParas at 1990:01F9, 1990:0202 and 1990:0212. 1990:0243 is `inc bx` on the copy's own MCB size, read at 1990:023F (`mov bx,ds:[3]`, ds = the copy's MCB at 1990:0234): the copy count is that size plus one, which equals the footprint. Cite the three reads, or the 023F to 0243 count, not 0243 alone.
- [x] should src/E1990.ASM:86-87 (CheckMemoryChain header): "DOS chooses the block it comes from (first fit)". The round 1 finding asked for no claim about which block DOS picks; the reply added "first fit". First fit is DOS's default allocation strategy, but nothing in this unit sets it (no INT 21h AH=58h in 1990:0000 to 02C5). Either say it is DOS's default strategy and that the unit leaves it unchanged, or drop "(first fit)".
- [x] should src/E1990.ASM:42 (gMcbSeg): "set by 1990:0071" names the function entry. The store is at 1990:0088 (`mov cs:[0Eh],ax` in CheckMemoryChain), as re/renames.toml:1333 says. - [x] should src/E1990.ASM:2 (unit header): "five scratch words" is not what they are. gMemTopSeg is written by ReserveMemoryBelowVideo and then by StartupGame (07C8:0212), and read by TrimMemoryToVideo at exit (07C8:060D); gVideoTopSeg, gMovedSeg, gMovedParas and gNewMemTopSeg carry values from one call to the next. Say "five state words".
- [x] should src/E1990.ASM:86-87, 258-260, 337 and 357-359 (the word "probe"): "the probe block" names the one-paragraph DOS allocation (1990:0079, 01BB, 0286), but the same word names the video probe in ReserveMemoryBelowVideo (probeDown, probeDone, probeEnd at 1990:0139 to 0150 and 210 to 240). - [x] should src/E1990.ASM:258-261 and 357-360 (QUIRK 1990:01CE and 1990:0296): "reached only when the probe block is the last block of the chain, which is not checked here" is unclear. The jump is taken when the probe's MCB type is not 'M' (1990:01C6 to 01CC; 1990:0294 to 0296). In a valid chain a block that is not 'M' is the 'Z' block, so the path is taken when the probe is the last block. - [x] should src/E1990.ASM:187-195 (ReserveMemoryBelowVideo header): (a) "Result is the top segment found (globals gVideoTopSeg, gMemTopSeg)": the function returns gVideoTopSeg after the step at 1990:0202 to 0207 (1990:0274 loads cs:[4] as the return value), and it does not return gMemTopSeg. - [x] note correction to the round 1 summary above: it lists "INT 21h 48h, 49h and 4Ah". The unit uses AH=48h and AH=49h only; there is no AH=4Ah in 1990:0000 to 02C5 (checked with tools/re/disasm.py). The unit header and comments do not mention 4Ah, so no source change follows from it.
- [ ] note src/E07C8.C (owner, not this unit; joins the open note from round 1): the local `memtop` at src/E07C8.C:188 is the return value of ReserveMemoryBelowVideo (gVideoTopSeg after the step at 1990:0202 to 0207), not gMemTopSeg, and it is then used as the segment of slots 2 and 3 at E07C8.C:220.
